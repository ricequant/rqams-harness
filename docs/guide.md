# Agent 业务翻译指南

这份文档给 Agent 用：用户说的是业务语言，`rqamsh` 操作的是 AMS 对象与端点。翻译的目标不是维护一张同义词表，而是让 Agent 根据**对象边界、动作效果和副作用**判断用户到底要什么；判断不了就问，不要猜。

它不是给业务用户读的。业务用户不需要阅读本文、`docs/`、`schema` 或错误码；安装好 `rqamsh` 后，由 Agent 按下方[首次使用流程](#使用方式用户说业务agent-读文档)主动建立连接，再继续用户原任务。未指定地址时优先沿用已保存的部署，没有保存地址才连接 RQAMS 官方地址 `https://www.ricequant.com`；首次连接私有化部署或切换部署时指定目标地址，完整优先级见[建立连接](connection.md#建立连接)。本文是 Agent 的内部判断规则，不是用户手册。

它不是 API 参考。参数、返回结构和默认值以运行时 `rqamsh schema` 与对应业务页为准；本文只约束“怎么从用户话里得到正确的对象、动作和读写计划”。

用户只问概念或能力、未请求连接或自己的数据时，读取相应概念说明，直接解释，不调用业务接口、不触发登录。新会话首次处理连接或业务数据时，先读下节与「1. 翻译要产出什么」，再开始业务调用。涉及估值、实时、批量汇总或分析时，执行前读取[任务完成条件](#task-readiness)；遇缺项、运行态、失败或超时，进入[等待与诊断](connection.md#unready-inputs)。准备写入时读取[写操作计划卡](#6-写操作计划卡)与目标操作的覆盖、失败及读回规则。同一会话已读且文档未变时复用，不要求每次全文阅读。

**本页讲规则，案例讲应用。** 对象与动作如何消歧、什么时候需要授权、什么证据足以交付，统一在本页维护；[核心学习案例](demo/README.md)用具体材料展示这些规则怎样改变下一步。不必顺序读完所有案例：先判断当前任务，再按需进入对应案例；案例中的具体计划卡与复查结果不是另一套通用规则。

## 使用方式：用户说业务，Agent 读文档

业务用户的最小路径是：让 Agent 安装并连接，首次在弹出的本机页面填写 key（Bearer 令牌），然后继续原任务；已有身份时无需再次填写。用户说“帮我安装”或“装好了”时，Agent 在安装与 `rqamsh schema` 检查后继续完成连接，不能把离线命令成功当作接入完成。用户只询问安装方法、概念或能力，未要求实际使用时，不启动登录。

第一次对话按这个顺序：

1. **主动发起首次连接，缺 key 默认打开本机登录页。** 直接执行与原任务相关的首个 CLI 只读命令；尚无具体查询时可用 `rqamsh workspaces list`。CLI 会复用已有设置或已提供的身份；缺少身份时默认打开浏览器，让用户在页面填写 key，成功后继续同一命令。也可先执行 `rqamsh auth` 建立登录再继续原任务。缺少 `RQAMSH_TOKEN` / `RQAMSH_BASE_URL` 不代表无法连接，不先索要 token 文件、管理员注入、服务地址或空间 ID；只有用户指定私有化部署时才传 `--base-url <地址>`。不要读取或回显设置文件中的 key，也不要让用户贴进对话。登录保存本机身份，不代表授权任何 AMS 业务写入。
2. **连接检查。** 首个命令失败时按错误区分连接、令牌、空间与资源权限；需要核对空间时用 `workspaces list`，它按当前 PAT 列出成员空间，不要求先选空间。没有明确指定空间时，零项报无可用成员空间错误；非空时使用服务端当次返回的首项，不排序、不按名称或 ID 取最小项、也不按 AMS 权益筛选。显式 `workspace_id` 或 `workspaces use` 只选择请求路由，成员关系、AMS 权益和资源权限仍由服务端逐项判断；选空间不增加权限。注入令牌不继承保存身份的空间，只有复用同部署保存身份时才沿用最后明确选择。私有部署返回 `No workspace specified` 时，先核对服务地址和部署入口，再请管理员提供该部署可用的空间 ID，不能靠重试或猜 ID 解决。规则见[空间选择](workspaces.md#默认工作空间与切换)。
3. **确认角色和第一个目标。** 只问一个能决定默认护栏的问题：你主要做组合查看、运营导入、研究分析，还是交易导入？用户已经说了目标，就从目标推断，再用一句话确认，不要重复问。
4. **先做一次只读。** 用用户提到的产品/组合；名称不唯一时列 2–3 个候选。第一次不要写。读完后按「结果翻译」回答对象、实际业务日期/as-of、来源、完整性和关键数字。
5. **只教一个概念。** 用刚看到的结果解释一个概念，例如“资产单元不是券商账户，它是产品内单独核算的一块资产，所以持仓单只做数量核对，不参与产品估值”。不要一次讲完产品/产品组/资产单元/账户配置/估值表。
6. **记住会话内的用户模型。** 角色、工作空间、常看产品、默认时间口径、是否接受写入；token 由运行环境或设置提供，不要在对话里重复保存或回显。后续直接使用这些默认值，减少重复提问。
7. **第一次写入更慢。** 先只读诊断，再给「写操作计划卡」，确认对象、范围、日期、覆盖/重复风险和读回方式；用户确认后才执行，执行后读回。
8. **逐步扩展。** 每次只引入一个新对象或新动作；用户没问到的业务块不主动展开。用户说“我不懂 AMS”时，不要发文档链接，用一句业务语言加一个例子解释，然后继续当前任务。

登录时保持命令进程运行，给用户留出填写时间；不能看到命令尚未返回就杀掉进程、重开登录或宣称无凭据可用。自动打开失败时，将 CLI 输出的本次登录地址交给用户在同一台机器打开，并保持进程等待；该地址不是 AMS 服务地址，也不能拿远程机器的本机地址直接给用户访问。超时后旧页面失效，需重新发起登录。

**仅明确远程、容器、无图形或无人值守执行时走注入方式：** 设 `RQAMSH_AUTO_LOGIN=0`，使用受限文件 `--token @文件` 或运行环境 `RQAMSH_TOKEN`。运行在 Agent 工具内、非 TTY、命令输出被捕获，均不能单独证明没有本机浏览器；没有这类限制时按本机默认流程执行，不凭猜测跳到“请管理员注入”。如用户已明确提供安全凭据来源，直接使用，不重新索取。

**Python 不代替首次登录：** `rqamsh.init()` / `Client` 缺少设置时只会报错，不自动弹页；多步业务可以用 Python，但本机首次先通过上述 CLI 流程登录，之后省略 `token` 复用保存身份。Python 不自动读取 CLI 的连接环境变量，规则见[建立连接](connection.md#建立连接)。

用户不需要做：

- 读 `docs/`、`schema` 或错误码；
- 记 API 名、参数名或业务块编号；
- 自己判断产品/产品组/资产单元/账户配置的区别；
- 自己决定实时还是历史、是否能重试；
- 在官方地址手工提供 `workspace_id`；Agent 按[成员空间与选择](workspaces.md#默认工作空间与切换)自动解析目标空间：零项无可用空间，非空则默认使用服务端首项，只有需要读别的分区时才由你指定。注入令牌不继承保存的空间。选定空间只是把请求发到该分区，不增加成员关系或资源权限；私有部署明确要求空间 ID 时由管理员提供，不让用户猜。
- 把 token 粘贴到对话里；Agent 直接运行业务命令，首次缺少设置时自动触发浏览器登录，用户在页面输入。

Agent 不要做：

- 用文档链接代替回答；
- 一次列全部业务块或全部操作；
- 一次问多个问题；
- 不确认就写；
- 猜对象、日期或净值口径；
- 让用户把 token 贴进对话或读取设置文件内容；
- 把未设置连接环境变量当作无法连接的依据；应按[首次使用流程](#使用方式用户说业务agent-读文档)复用已有设置或发起本机登录；
- 将浏览器填 key 误称为不支持的账号密码代办登录，从而拒绝打开本机页面；
- 把空结果/未就绪说成 0；
- 把 401/403 一概说成“系统坏了”。

首次对话可以很短：

```text
用户：装好了。
Agent：我先连接 AMS。首次使用会打开本机页面，请在那里填写 key，不要发到对话里。
（Agent 实际执行 rqamsh workspaces list，并保持进程等待。）
用户：（在网页填写并保存。）
Agent：（成员空间查询成功后）已连接。你现在想查看什么？
```

若用户已说“查询所有有实盘的产品和规模”，登录后直接继续定位实盘产品及读取规模，不再问角色或重复索要目标；范围有业务歧义时先连接并读取可见信息，再只澄清真正影响结果的口径。

首次只读按[结果翻译](#7-结果翻译)交付，至少说清对象、实际业务日期/as-of、来源和完整性；不是“API 返回 200”。

## 1. 翻译要产出什么

对一句用户请求，先补齐六件事：

|要素|要回答的问题|
|---|---|
|对象|是产品、产品组、资产单元、账户配置，还是某类持仓/报告？|
|动作|要看、要导入、要改、要算、要封账，还是要授权？|
|范围|单只产品、产品组、某个资产单元，还是全部可见资源？|
|时间|业务日期是哪天；要实时、最近结算日，还是历史区间？|
|读写|只读，还是会改变业务数据或触发计算？|
|确认|是否需要计划卡、用户确认和读回验收？|

六件事没有补齐时，不要直接调用写操作。缺对象或动作时，先问一个能决定分支的问题。

## 2. 先判断对象边界

AMS 里几个词最容易混。不要按字面相似度映射，按**核算边界、数据来源和可操作性**判断。

|用户可能指的东西|AMS 对象|判断要点|不能做什么|
|---|---|---|---|
|基金、资管计划、组合、产品|产品|独立核算边界；有产品 ID|产品组不能代替成员产品写入|
|多只产品汇总|产品组|只用于汇总/分析；成员是产品|不能把产品组当成批量写入口|
|产品内单独核算的一块资产|资产单元|属于一个产品；目前只用于收益互换底层组合|不是新基金，不是券商账户|
|交易/托管账户|产品内的账户配置|挂在 `product.accounts[]` 下；没有独立全局 ID|不能作为 `resource` 单独选择|
|持仓、头寸|多来源|先问是系统头寸、估值表持仓、产品持仓表，还是资产单元持仓单|不同来源的写入副作用不同|
|估值表、估值报告|估值报告|可含净资产、单位净值、分类份额；可驱动估值|不要和产品持仓表、持仓单混用|
|持仓表|产品持仓表|产品级 JSON 截面；同日已有估值表覆盖时不写入|不是资产单元持仓单|
|持仓单|资产单元持仓单|资产单元级；只做数量核对|不参与产品估值，不触发重算|
|模拟交易、模拟盘、信号|模拟交易产品|按模板创建；信号进入模拟撮合后生成流水|不是真实委托；不能下单或执行交易|
|对账|对账记录/差异|可能只是查差异，也可能是标记或采用覆盖|`mark`/`auto` 是写操作|
|净值|单位/累计/复权净值|口径不同；必须带日期和实时/历史语义|不能把累计净值当单位净值|
|重算|计算任务|提交任务与读取状态是两件事|提交成功不等于算完|

### 2.1 持仓的四个来源

用户说“持仓”时，先按来源拆：

|来源|典型读取|层级|写入后的影响|
|---|---|---|---|
|系统计算头寸|`balances.get`|产品/产品组|由流水、估值和计算状态决定；资产单元内容通过所属产品的穿透结果查看，不能直接把资产单元作为 `resource`|
|托管估值报告里的持仓|`valuation_reports.*`|产品|可能影响估值与后续计算|
|产品持仓表|`positions_sheets.*`|产品|同日已有估值表覆盖时不写入；否则可作为估值截面输入|
|资产单元持仓单|`positions_statements.*`|资产单元|只做数量核对，不参与估值、不触发重算|

判断顺序：先问“你要核对数量，还是要看估值后的头寸，还是要导入一份文件？”再落到具体对象。

## 3. 再判断动作效果

不要按动词字面匹配。问“这个动作会不会改变数据，改变什么”：

|用户意图类别|判断问题|读写属性|
|---|---|---|
|看、查、为什么、怎么样|只是读结果，还是要创建归因/分析任务？|读取只读；创建任务按写操作处理|
|导入、上传、录入、更新|导入什么文件、哪一天、是否覆盖同日数据？|写|
|对账|只看差异，还是要标记结论/采用估值表覆盖？|前只读，后写|
|重算、刷新|只查计算状态，还是提交重算？|查只读，提交写|
|封账、解封|封哪只产品、哪一天？|写|
|授权、分享、收回|对哪个资源、哪个用户、什么级别？|写|
|导出|只是本地生成文件，还是要写回 AMS？|通常只读；写回另算|

一个请求里可能同时有读和写。先做只读诊断，再对写操作给计划卡；不要因为前半句是“看一下”就跳过写操作的确认。

同一个动词也可能有不同效果。“导、拉、发、传、补、更新”既可能是查看、导出到本地，也可能是写回 AMS。先按“会不会改变 AMS 数据”判断动作，再判断对象；不要默认成导入，也不要直接跳进对象/来源选择。动词多义优先于对象选择：先定动作，再定产品/单元/文件类型。

### 3.1 不在范围内的请求

投资建议、择时、下单和交易执行不在 Harness 的范围内。用户问“能不能加仓/买/卖/这个信号能不能下单”时：

- 先明确说不能给投资建议、不能执行交易；
- 再说明可以提供哪些只读数据（头寸、持仓、收益、风险暴露）；
- 不要把“帮你判断加仓”包装成本项目的能力。

## 4. 消歧规则

真实说法是开放集合，下面的规则比词表更重要：

1. **一词多对象**：按边界问，不按同义词问。  
   例：“账户”可能是产品内配置，也可能是用户口语里的资产单元。问“你要看产品内配置，还是产品内单独核算的资产单元？”
2. **一词多动作**：按效果问。  
   例：“对账”可能只是查差异，也可能是标记结论或采用估值表覆盖。问“你要只看差异，还是要改变对账状态？”
3. **缺少范围**：问产品/产品组/资产单元；不要默认“全部”，更不要把写操作广播到产品组。
4. **缺少时间**：问业务日期。用户说“今天/最新”时可以按该口径继续，但要明确说出假设；历史区间必须确认起止日。
5. **角色与动作冲突**：角色只决定默认模式和护栏，不替代服务端权限。基金经理要求写入时，必须显式确认“这是写操作，会改变数据”，不能因为角色是只读就拒绝，也不能静默执行。
6. **一次只问一个决定性问题**：给 2–3 个选项，每个选项说明后果（只读/写入/触发计算/覆盖范围）。不要一次抛五个问题。
7. **仍然无法判断**：说明缺什么信息，不要编造对象或操作。可以给出最接近的只读诊断，但不要猜测写入。

### 4.1 澄清顺序：一轮只推进一层

信息不足时，先找出“哪一层不确定会改变操作分支”，只问那一层的一个问题：

1. **动作层**：先判断是查看、导出到本地，还是写回 AMS；如果动词本身有歧义，先定动作。
2. **对象层**：再定产品、产品组、资产单元或账户配置。
3. **范围与时间层**：再定单只/组/单元、业务日期、实时/历史口径。
4. **参数层**：最后定文件类型、账户、净值口径、标的/因子、覆盖方式等执行参数。

对象未定时，不要先问日期、净值口径、文件类型或标的代码；这些属于参数层，先确认核算主体。用户说“这个产品/这只产品”时，先解析成唯一产品 ID 或名称；名称不唯一就列候选，不要用价格、代码或账户名代替产品。

用户已经给出时间词（“今天/本周/最新”）时，不要先重复问日期；先确认对象，把日期假设写进计划卡或回答里。写操作先确认对象，再问文件类型/参数；不要先问“哪种文件”却还不知道写哪只产品。

“拉/导/发/传”没有说明去向时，先问是查看、导出到本地，还是写回 AMS；再问对象与来源。这个顺序优先于直接问产品/文件类型。

其它必要信息不要在同一轮并列追问。可以说明“确认这一点后，我再和你核对日期/口径”，把它们留到下一轮或写操作计划卡的待确认项。判断顺序不是固定的：如果动作本身会改变对象选择，就先问动作；核心是**一轮只让一个答案改变下一步**。

### 4.2 时间语义：先定“哪一天、什么口径”

用户说“今天、最新、实时、收盘、这周”时，不要直接当成某个日期。先判断：

| 用户说法 | 可能含义 | Agent 要做什么 |
|---|---|---|
| 今天 | 北京时间当天；也可能是用户本地日期 | 默认北京时间当天；跨时区或跨日先确认 |
| 最新 | 最新已结算、最新可用，或刚提交的实时结果 | 说明取的是实时还是最近结算，不把“最新”说成“今天已结算” |
| 实时 | 当前可用快照，不是日终历史 | 按实时语义读取；回答带实际返回日期与可用的更新时间/结算状态，不把请求时间当行情时间 |
| 收盘 | 收盘后，但估值/计算可能未完成 | 先查计算状态或未就绪字段；未就绪不是零 |
| 历史某日 | 业务日期 | 传过去日期；返回日期不一致时按 `historical_date_mismatch` 处理 |
| 估值日/报告日 | 估值报告所属的业务日期，不等同写入时间 | 以报告返回的 `date` 为准，不拿上传时间代替 |
| 未来日期 | 不是有效业务日期 | 不要传未来日期；改用今天实时或已过去的历史日期 |
| 这周/本周 | 区间，起止边界可能不同 | 边界影响结果时先确认起止日，不自行假定 |
| 上一交易日 | 最近一个已结算交易日，不等于“昨天” | 用上一交易日概览；不替代今天实时或指定历史日 |

几条硬规则：

- **业务日期、请求日期、实际返回日期分开。** 回答用实际返回日期；不能用请求日代替结果日。
- **实时不等于历史日终。** 不能用实时结果冒充某日结算，也不能用上一交易日概览顶替当日结果。
- **夜盘可能归属下一交易日。** 以返回值里的业务日期为准，不按请求时间推断。
- **交易日与自然日分开。** 不要用 7 个自然日推算 5 个交易日；区间和日历按业务页定义。
- **净值所属日期与发布/更新时间分开。** 不要把请求日当成净值日，也不要把更新时间当成估值日。
- **未就绪的三种状态分开。** `pending_valuation`、`error_messages`、`has_settlement` 含义不同；缺结算价不等于整条结果未就绪。
- **回答至少带**：对象、实际业务日期/as-of、实时/历史、来源、完整性。

<a id="task-readiness"></a>
### 4.3 任务完成条件：不是调用成功就能交付

涉及估值更新、实时查询、批量汇总或分析未就绪时，先按[估值主线](index.md#valuation-lifecycle)定位当前阶段，再选择操作。不能从“接口返回成功”直接跳到业务结论：

|用户目标|不足以证明完成|交付前核对|
|---|---|---|
|查看全部产品当前规模|批量请求成功，或只返回部分产品|按请求集合核对每只产品的当日实时结果、字段和更新时间；未返回项按[未就绪处理](connection.md#unready-inputs)等待或诊断；完整前只能称已就绪部分的小计|
|导入流水或估值表后查看净值|上传、解析或登记成功|逐项导入结果、报告日期及采用方式正确；后续计算完成，目标日期的头寸和净值已读回并符合预期|
|更正历史后确认结果更新|修改成功，或只核对被修改当天|按输入规则确认受影响范围，检查计算状态，并读回用户关心的后续日期；不能将更正前的结果当作更新后结果|
|解释收益或风险差异|任务已提交，或已有净值、期末持仓|所需指标、历史或实时分析结果就绪，区间、基准和模板一致；未取得归因证据时，不把持仓差异直接说成收益原因|

对尚未完成的任务，用用户目标解释进度，例如“剩余产品的实时结果尚未就绪，我会继续检查，已就绪部分先保留，完整后再汇总”；只有确认正在计算时才说“正在计算”。明确失败、缺资料和达到等待上限时，分别说明原因、需要补什么或最后状态，不把它们统称为计算中。具体判断与重读方式只按[等待规则](connection.md#unready-inputs)执行，不为取得答案擅自补造输入或提交重算。

## 5. 角色原则

角色用于调整默认行为和提示重点，不是权限白名单。

|角色|默认|关注|护栏|
|---|---|---|---|
|基金经理|只读|持仓、收益、回撤、归因|先确认实时还是最近结算日；归因说明区间、基准、模板；写入必须显式要求|
|基金运营|写前确认|估值表/持仓表/持仓单、对账、封账、申赎|先给计划卡；说明同日覆盖；部分失败按逐项/覆盖式分别处理；封账/解封确认业务日期|
|研究员|只读|持仓结构、行业分布、因子暴露、归因|注明分类标准；区分实时截面与逐日历史；缺数据不要补零|
|交易员|写前确认|成交导入、导入状态、交易分析、行情|导入前查同日记录；失败不盲目重传；确认普通流水/日内文件/交割单|

角色不改变服务端授权。越权仍由平台拒绝；不要用“换一个同名资源”绕过权限。

## 6. 写操作计划卡

任何写操作执行前，先形成计划卡。计划卡是调用方护栏，不是服务端授权。

```text
对象：具体操作支持的真实目标类型（产品/产品组/资产单元/标签/授权行等）名称与 ID；新建时注明待生成 ID，不要只用名称
范围：单只产品、产品组本身、成员集合还是资产单元；成员业务数据不因产品组写而广播
日期：业务日期（如适用）；是否覆盖同日数据
动作：具体操作链
会改变什么：估值/流水/对账状态/权限/封账范围
重复与覆盖：同日已有数据怎么处理；失败项是否已写入
确认级别：none / required
读回：操作后用哪个只读操作核对哪些字段
失败时：是否保留 task_id；是逐项补失败项，还是覆盖式导入必须重传完整范围；是否禁止盲目整批重传
```

执行顺序：

1. 只读诊断：列可见资源、查同日数据、查计算状态。
2. 给计划卡，等确认。
3. 执行写操作。
4. 读回验收；部分失败时先判断逐项还是覆盖式，再按对应方式处理。
5. 结果翻译成业务语言，不只报“成功/失败”。

禁止：

- 用名称直接写；名称有歧义时先解析成 ID。
- 把产品组当作批量写入口。
- 写请求超时后直接重放；先确认原请求是否已产生副作用。
- 把部分失败一律按“只补失败项”处理。逐项写入（如结构化流水 upsert）可只补失败项；覆盖式文件导入（如券商日内/结算文件、托管事件 `upload_file`、按日期整段替换的持仓表/持仓单）必须按该操作要求的完整范围重传，先读回并确认覆盖区间，否则会删掉同区间已成功的数据。
- 把 `effect_count = 0` 一律解释为失败；也可能只是内容未变化。

## 7. 结果翻译

返回 JSON 不是答案。至少翻译这些语义：

交付前按四项组织回答，并逐项对照实际读回与权威定义：

|回答组成|必须说清|证据边界|
|---|---|---|
|对象与时间|目标对象、实际业务日期、实时或历史、可用的更新时间及来源|更新时间的含义查对应字段，不把请求时间当数据时间；解释估值推进时按[估值主线](index.md#valuation-lifecycle)，不套用指标统计日历|
|已核验结论|用户需要的关键数字与单位；比例按正确尺度展示|涉及净值、收益、风险或暴露，先查权威字段或指标行；计算核对只验证该关系，不增加数据来源证据|
|解释与依据|事实、解释和待验证假设分开|只有配置差异或期末截面时，只陈述观察到的差异；具体因果结论需对应历史、事件或归因证据|
|完整性与下一步|本次哪些结果已就绪、哪些缺失或未验证、接下来如何处理|所请求字段齐全及内部勾稽通过，不证明交易、报告、行情等全部输入齐全，也不等于已封账或可对外披露；没有执行证据的部分明确标注未核验|

收益与净值不是同一个概念：`daily_returns` 是收益率；`unit_net_value` 是单位净值，其环比不是收益率。用户问“收益/涨跌”时用 `daily_returns`；问“净值变化”时给单位净值变动，并明确它不是收益率。

|字段/状态|翻译要点|
|---|---|
|`unit_net_value`|单位净值，不是累计单位净值；其环比不是收益率；带日期与实时/历史口径|
|`acc_unit_net_value`|累计单位净值，不是单位净值|
|`adjusted_net_value`|复权净值，口径与上面两者不同|
|`total_equity`|净资产；可用“总资产 - 总负债”做守恒检查|
|`daily_pnl`|金额，不是收益率|
|`daily_returns`|收益率，不是金额；优先直接使用，不要用单位净值或净资产变化率替代；注意区间与复利口径|
|`positions`|持仓明细；说明来源是系统头寸、估值表、持仓表还是持仓单|
|`pending_valuation`|请求但未返回、且未列入明确错误的成员/产品；不证明它们都在计算，按[未就绪处理](connection.md#unready-inputs)判断|
|`has_settlement`|结算数据是否就绪；缺数据先报缺口，不要补零|
|`error_messages`|按对应操作解释逐项失败原因；可能是读取或计算失败，不能一概说成未写入；非空时不要只看成功项|
|`effect_count`|实际影响条数；0 不一定是失败|
|`task_id` / `compute_state`|任务标识或计算状态，不是结果完整性的证明；仍需按[任务完成条件](#task-readiness)读回验收|

通用规则：

- **缺失不等于零**：空列表、null、未就绪都先说明缺口。
- **金额、份额、净值、收益率分开说**：不要混用单位。
- **日期与口径必须带**：业务日期、实时/历史、单位/累计/复权。
- **来源必须带**：系统计算、托管估值、产品持仓表、资产单元持仓单。
- **部分成功必须逐项说**：哪些写入、哪些跳过、哪些失败。
- **不确定的副作用保留“可能”**：部分失败后重放、覆盖同日数据、异步任务是否仍在运行，都不能写成必然结果；先读回再判断。

## 8. 错误翻译

错误码先分类，再决定是否重试：

|错误|用户语言|下一步|可重试|
|---|---|---|---|
|`permission_denied`|没有权限|确认资源可见；写入找管理员授权；不要绕过|否|
|`resource_not_found`|找不到资源|先列可见资源让用户选；仍找不到就报权限/范围缺口|否|
|`ambiguous_resource`|名称有歧义|列候选 ID，让用户确认；不要任选|否|
|`invalid_config`|连接配置缺失或非法|区分缺 key、非法参数与部署不匹配；本机缺 key 按[首次使用流程](#使用方式用户说业务agent-读文档)主动发起登录，不把环境变量缺失当作阻塞；明确无图形/远程执行才用安全注入；其他错误修正对应配置|否|
|`historical_date_mismatch`|返回的业务日期与请求日不一致|保留请求日与实际日；不能把结果当请求日|否|
|`unsupported_resource`|资源类型不支持|换正确类型；产品组不能代替成员产品写入|否|
|`wait_timeout`|等待超时|服务端可能仍在跑；保留 `task_id`；写请求先查结果|是，但写操作先读回|
|`task_failed`|服务端任务失败|保留错误与任务 ID；修正输入后重提|否，改输入后再说|
|`partial_failure`|部分写入失败|先判断逐项还是覆盖式：逐项只补失败项，覆盖式按完整范围重传；两者都先读回，成功项通常不会回滚|否|
|`pending_without_task`|待处理但没有任务 ID|停止重试；读回目标数据确认状态|否|
|`transport_error`|网络/连接错误|只读可确认无副作用后重试；写先读回|是，分读写|
|`invalid_response`|返回结构不符合预期|保留状态码与响应片段；核对版本|否|
|`http_error`|服务端非成功状态；401 通常是 `API Key 无效`/令牌过期，403 是权限，404 是路径或资源不存在，422 `No workspace specified` 是该部署未能确定请求分区|先看状态码：401 重新取得 Bearer 令牌，403 查权限，404 核对路径/资源，422 先确认地址对应正确部署、所选空间属于该部署（见[空间选择](workspaces.md#默认工作空间与切换)），仍无法确定时让管理员提供该部署的空间 ID；5xx 保留诊断|视情况|

## 10. 与 API 文档的分工

- 本文负责：对象边界、动作效果、消歧、读写判断、计划卡、结果/错误翻译。
- 不知道用户目标属于哪个业务阶段时，先用 `docs/index.md` 的“一条主线”定位，再回到本文做对象/动作翻译；不要从操作清单反推业务。
- `rqamsh schema` 与业务页负责：精确参数、返回字段、默认值、覆盖规则。
- 找不到对应操作时，明确说“当前 Harness 不覆盖”，不要用相邻操作替代。
- Agent 每次应读取当前仓库文档与 `schema`，不要依赖记忆中的旧字段。
- 本文不维护同义词表；例子只用于说明判断规则，新增说法不需要逐条登记。
- 本文维护通用规则与空白计划卡；案例维护填入具体对象、日期、证据和预期结果的应用。案例不复制通用规则全集，本文不复述完整案例。

## 11. 维护原则

- AMS 语义变化时更新本文；用户换一种说法时，不需要更新本文。
- 新增示例只在它揭示新的判断规则时加入，不堆积同义句。
- 保持与 `rqamsh schema` 的业务块/操作清单一致；能力边界以 [docs/index.md](index.md) 为准。
- 新增或删除业务块时，同步更新 `docs/index.md` 的主线表和业务块导航；两处漏一处就会让 Agent 定位错阶段。
