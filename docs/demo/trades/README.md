# 流水处理场景：从首次历史接入到持续维护

先确定用户是第一次接入，还是维护已有头寸链，再按操作及流水来源选择案例。目标不是把接口都调用一遍，而是让真实业务输入在正确日期、账户范围内进入估值，并能解释修订、结算和迟到报告之后的结果。本页导航，参数与替换契约仍由[流水业务页](../../trades.md)维护。

## 首次接入已有历史

[已有完整历史流水，怎样建立并接续头寸链](initial-import/README.md)：盘点成交之外的资金、费用、份额和权益输入；选定真实起点，分批导入并核验关键日期；再批量同步上游修订和新增记录，最后接入历史截止点后的新成交。中途截面与从头重建分开，不重复应用截面已经包含的成交。

<a id="synchronization"></a>
## 持续同步与近期维护

|来源与来件条件|业务问题|学习案例|
|---|---|---|
|OpenAPI；纯流水或混合产品|持续取得成交及其修订，怎样直接批量同步而不逐笔查询 AMS ID？|[稳定外部键的持续同步](synchronization/openapi/README.md)|
|日内文件；混合产品报告迟到|上午、下午文件怎样更新有效成交？差量为什么不能当完整替换文件？|[完整日内文件替换与修订](synchronization/intraday-file/README.md)|
|只有盘后结算文件|盘中能交付什么，盘后怎样确认结算成交进入估值？|[仅结算文件的维护](synchronization/settlement-file/README.md)|
|日内文件与结算文件先后到达|同日成交怎样由结算接管，晚到日内文件怎样处理？|[日内到结算接管](synchronization/intraday-and-settlement/README.md)|
|混合产品的迟到估值报告|保存与采用怎样区分，校准后怎样继续应用后续成交？|[报告校准与继续接续](synchronization/valuation-report/README.md)|

纯流水产品依靠业务变动维护；混合产品还要明确报告采用到哪一天、后续哪段由流水维护。外部系统或外部模拟策略同步成交，不等于让 AMS [模拟交易模板](../../paper_trading.md)再次撮合信号。历史估值与实时截面也分开核验，不能因输入已保存就宣称盘中全部就绪。

<a id="correction"></a>
## 修改已有流水

|来源|业务场景|案例范围|
|---|---|---|
|OpenAPI（`open_api`）|[一笔错单的量价修改与估值影响](correction/openapi/README.md)|定位原记录，只修改获准数量和价格；保留另一笔成交，读回更正前基线、更正日及后续日的估值。含脱敏实测数据，不代表文件修订流程。|

这篇单笔案例的入金和两笔成交是它自身的测试准备，不代表已验证批量同步；批量同步的输入、独立执行与证据由前述新案例维护。不用删除重录代替获准的局部更新，也不将已知 ID 的修改支线当作 OpenAPI 同步的必经步骤。

## 从对账或收益异常进入

- [对账案例](../reconciliation-controls/README.md#41-数量不一致沿历史持仓追到错误源头)负责查明差异来源及原业务日。上游有稳定外部键时进入[批量同步](synchronization/openapi/README.md)；人工只更正一笔已知记录时参考[修改路径判断](correction/openapi/README.md#choose-write-path)，文件问题进入相应文件案例。完成后按原对账范围复查，不用“上传成功”替代差异闭合。
- [收益异常案例](../returns-diagnosis/README.md#区间核对五项)负责区间与口径判断，不能用成交现金差替代收益率。追到已有流水错误时，再选择对应修改场景。

新场景共用一份[脱敏受控 SDK 证据](evidence.json)，原单笔更正仍使用其同目录证据。人工输入、服务端结果和未触发分支分别说明，不把历史日期链验证称为实时性能证明或自主 Agent 任务完成。参数和字段以[流水业务页](../../trades.md)与[流水字段页](../../fields/trades.md)为准，不在对账等案例复制另一套流水教程。
