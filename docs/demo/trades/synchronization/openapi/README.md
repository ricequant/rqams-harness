# OpenAPI 持续同步：让上游成交及修订持续进入头寸链

外部交易系统或外部模拟策略已经产生真实业务成交。用户希望 AMS 持续反映这些成交，并在上游修订历史记录时一起更新。主线是稳定业务键的批量同步，不是每次查找 AMS ID 再逐笔修改。

## 1. 先确认接续基础

首次接入时先完成[历史建账](../../initial-import/README.md)，明确已确认覆盖到哪个业务日和上游版本。本例的另一条混合产品路径从 2026-06-26 的现金报告截面开始，近期成交由 OpenAPI 提供；产品 `auto_overwrite=false`，报告保存和采用分开进行，见[报告校准](../valuation-report/README.md)。

数据源须允许流水。账户使用产品配置中的实际账户；外部成交要带实际业务时间、代码、交易类型、数量、未复权成交价、费用和稳定外部编号。自动生成权益、资金及份额事件按实际来源衔接，不能以“成交接口同步了”证明所有输入齐全。API 字段见[上传](../../../../trades.md#upload)。

## 2. 首批同步后，确认成交确实进入结果

本例先收到 06-29 买入 `000001.XSHE`，100 股、10 元、佣金 5 元。按外部编号上传一次，检查逐项结果，再按原日期、账户读回有效流水和当日头寸。

```python
trade = {
    "datetime": "2026-06-29 10:00:00", "transaction_type": "buy",
    "asset_class": "stock", "order_book_id": "000001.XSHE",
    "quantity": 100, "price": 10, "commission": 5, "tax": 0, "other_fees": 0,
    "currency": "CNY", "exchange_rate": 1,
    "account": account, "foreign_id": "<外部键-mixed-1>",
}
receipt = rqamsh.trades.upload(resource=product_id, data=[trade])
```

`product_id` 与 `account` 均来自本次已核验目标；尖括号外部键为不可直接提交的脱敏别名，须替换为上游稳定编号，修订时保持同一编号。已有初始资金为 1,000,000 元时，本笔使现金变为 998,995 元、持仓为 100 股。按当日实际估值价核对市值及净资产，不能用成交金额当资产损失。

## 3. 修订和新成交一起到达，不先筛选哪些记录在 AMS 已存在

上游将原买入修订为 120 股、11 元，佣金不变；同时提供 06-30 卖出 40 股、12 元、佣金 5 元。两条完整记录可以同批提交：

```python
revised = dict(trade, quantity=120, price=11)
new_trade = dict(trade, datetime="2026-06-30 10:00:00", transaction_type="sell",
                 quantity=40, price=12, foreign_id="<外部键-mixed-2>")
receipt = rqamsh.trades.upload(resource=product_id, data=[revised, new_trade])
```

同产品非空 `foreign_id` 做 upsert；账户不同不构成另一套外部键空间。上游各渠道编号冲突时，先形成稳定命名空间，不能简单换键来“修复”旧记录，否则会新增重复业务。已授权字段之外的业务变动仍要核实；批量上传不是任意历史覆盖授权。

随后核对原买入已修订、卖出新增、没有重复成交。现金在买入日为 998,675 元，卖出日为 999,150 元，目标持仓依次为 120 股、80 股；净资产变化还取决于对应日期估值价。历史修订从受影响日向后更新，等待与封账边界见[输入变更与重算](../../../../index.md#valuation-recompute)。

纯流水产品一直依靠这些业务变动向后维护；混合产品还要明确哪些历史日期已采用报告，不能忽略报告对结果的影响。需要人工仅改已知 ID 的量价时，使用[局部更正案例](../../correction/openapi/README.md#choose-write-path)，不要把该支线升级为持续同步的必经步骤。

## 4. 同步异常怎样继续

|观察|判断与动作|继续前的证据|
|---|---|---|
|批量回执含逐项失败|无错误且返回记录 ID 的成功项已经写入，不因其他项失败回滚；按逐项错误核对失败输入|有效流水与输入逐项对应，成功 ID 与失败详情完整保留|
|超时且无回执|未知是否写入；保留外部键、业务字段及提交范围，只读查询|查明已落库项后再决定重试，不要求不存在的回执 ID|
|上游撤销一笔|新批次缺一项不等于删除|定位原记录并确认删除授权，核验实际删除与估值影响|
|同日已有结算流水，上传被拒|该范围已进入结算文件维护流程|回到[结算修订](../settlement-file/README.md)，不换来源或换外部键绕过|
|只有成交快、其他必要输入仍慢|同步及时性不等于整份头寸完整|列出缺失事件及影响，不承诺完整实时结果|

同产品以相同非空外部键成功重发相同完整业务内容，预期更新原记录、保留 ID，不新增重复成交；仍会自动提交计算，不会因内容相同而跳过请求。该行为已在[首次历史接入实测](../../initial-import/README.md)中验证：重发后四条流水及各检查点业务结果不变，计算批次从 2 变为 3。字段修订、无外部键和失败项的处理见[上传契约](../../../../trades.md#upload)。不要为了等待估值就重发输入；资金入账、卖出、修订分别按业务事实处理，不能用相互抵消的假成交掩盖差异。

## 5. 报告到达后继续接续，而不是结束维护

混合产品的报告在成交之后才到达，按[保存、采用及后续传递](../valuation-report/README.md)处理。采用后还会有新交易，仍使用不同的稳定业务键继续同步。本例随后在 07-01 买入另一只股票，核验报告日不变、后续日新增正确，而不是把“采用报告成功”当整条链完成。

历史头寸和今天实时截面不是同一产物。实际生产任务还须读取目标实时结果、记录时点和成交覆盖范围，不能凭 `compute_state=normal` 宣称盘中已经全部更新。本页短历史受控 SDK 执行只验证日期链，未证明盘中端到端时延；原始输入与脱敏读回见[场景证据](../../evidence.json)。

本轮混合产品的实际读数位于 `lanes.mixed.stages`，下表金额为元，流水总数按整个测试区间统计。各阶段均未更改产品自动采用设置。

|实际阶段|核验业务日|有效流水总数|平安银行数量|现金|净资产|
|---|---|---|---|---|---|
|首批同步|06-29|1|100|998,995|1,000,019|
|历史修订与新增卖出同批同步|06-29|2|120|998,675|999,903.80|
|同上，核验后续日|06-30|2|80|999,150|999,954|
|报告已采用，再接入另一证券买入|07-01|3|80|997,070|1,001,473.80|

最后一阶段还持有招商银行，数量、成本和市值见完整明细；净资产不只由表中平安银行组成。报告校准的实际影响单独在[报告案例](../valuation-report/README.md)解释，不将不同输入阶段混成一次同步效果。
