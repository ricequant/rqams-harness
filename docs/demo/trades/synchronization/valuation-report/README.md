# 迟到估值表：从流水维护结果到报告校准，再继续接续

混合产品的估值报告通常晚于成交材料到达。近期先用流水维护；报告到达后，先解释差异，再决定是否采用。**报告不是另一批成交，不能作为增量资产加到原持仓上。** 本例用历史业务日期模拟到达顺序，不声称复现了某次真实盘中时点。

## 1. 先明确目前哪段历史采用了什么输入

本例产品为 `trade_and_valuation_report`、`auto_overwrite=false`：先保存并明确采用 06-26 的现金报告，作为 1,000,000 元、1,000,000 份的起点；06-29、06-30 随后依靠[OpenAPI 成交同步](../openapi/README.md)推进。到达顺序与报告业务日期分开记录，迟到材料仍写其原业务日。

切换产品自动采用设置会影响已有报告，不是“仅开启未来上传”的演示开关。本例保持该配置不变，用[明确采用某日报告](../../../../reconciliation.md#auto)限定日期，先确认写入授权；创建时初始化报告另有规则，不套用到每次后续报告。

## 2. 报告到达：先保存、比较，不立即掩盖流水差异

上游报告显示 06-29 股票仍为 120 股，现金与 AMS 流水维护结果有差异。先保存采用前的产品配置、当日及后续头寸、原始报告和流水范围；核对报告日期、账户覆盖、持仓、现金与资产负债，不从差额直接断言是漏成交。

```python
receipt = rqamsh.valuation_reports.upload(resource=product_id, data=report)
saved_reports = rqamsh.valuation_reports.list(resource=product_id)
```

`report` 必须来自本次已核实材料，满足[报告输入字段](../../../../valuation_reports.md#upload)，不是从 AMS 差额倒算的调平文件。文件输入使用支持的估值表模板。同日报告替换授权与是否采用是不同机制，不能用 `is_overwrite=True` 开启估值表采用。

本例关闭自动采用，保存后应在报告列表找到该日期及回执 ID；还须读回同日及后续结果，确认“保存了”没有被误说成“已校准”。通过替换授权与日期校验并取得写入回执后，已保存的报告不会因客户端针对解析错误抛出的部分失败异常撤销；解析整份拒绝或这些校验失败时不进入保存。保留实际回执并读回核对，规则见[报告上传](../../../../valuation_reports.md#upload)。

## 3. 明确采用后，核验报告日和后续链

确认业务要采用这份报告且差异已披露后，只处理获准日期：

```python
result = rqamsh.reconciliation.auto(resource=product_id, date="2026-06-29")
state = rqamsh.products.compute_state(resource=product_id)
```

`auto` 返回空响应，`compute_state` 单次读取也不等待。按[等待与停止条件](../../../../connection.md#unready-inputs)确认估值就绪，再读取报告日、下一业务日和用户关心的后续结果，同时查询[对账列表](../../../../reconciliation.md#list)确认采用标志；标志不是财务核验结论。

采用会按报告规则校准该日状态，而非再买入一份报告持仓。报告未列出的旧持仓、现金及净资产各按[估值表覆盖影响](../../../../reconciliation.md#valuation-report-overwrite-setting)处理。覆盖日产品盈亏按净资产变动扣除托管净现金调整计算，不按逐仓盈亏求和，两种口径不能强制相等。本例报告保留相同股票数量，单独构造现金差异，便于观察保存与采用两个阶段；这不证明差异来自某笔真实费用或上游漏单。

后续日期从校准后的状态继续应用其后的业务输入。本例 06-30 已有卖出，必须确认没有再次套用报告日前成交，也没有遗漏这笔报告日后的卖出。只看报告日净值对上不够。

## 4. 再来一笔成交，证明链能够继续

采用后，07-01 再同步另一证券的买入，使用新外部键、原交易账户和真实业务日。检查新日期持仓和现金正确，同时确认已校准报告日保持不变。这才完成“流水维护近期 → 迟到报告校准历史 → 后续流水继续”的链路。

文件来源也按相同原理衔接，但有效流水的替换规则仍归[日内文件](../intraday-file/README.md)、[结算文件](../settlement-file/README.md)及[日内与结算接管](../intraday-and-settlement/README.md)维护；不能将报告采用当作文件批次修复。

## 5. 交付必须保留原因与边界

- 分别回答报告已保存、已采用、估值已就绪、业务差异已解释到什么程度。报告采用后数值一致，不能据此宣称原流水完整正确。
- 报告本身有问题时取得修订材料和对应授权，不随意关闭自动采用、删除报告或用现金调整抵消。
- 报告日落在起始日之前或封账范围内时，遵守[采用校验](../../../../reconciliation.md#auto)，不擅自解封。
- 历史结果可读不代表当前实时截面就绪；实时要求仍需实际读回对应时点结果。

人工构造的报告和脱敏 SDK 记录见[场景证据](../../evidence.json)。它验证日期链上的保存与采用，不证明真实客户报告的经济来源、所有估值表模板或实际延迟时长。

## 6. 实际结果：保存没有校准，采用后向后承接

报告人工设定为 06-29 现金 998,600 元、股票 120 股，股票市值 1,228.80 元、含费用成本 1,325 元；股票同时提供 `quantity` 和 `cost_price`，不是把成本总额代替单位成本键。输入见 `lanes.mixed.inputs.late-report-save-corrected`。现金差异是教学设定，不归因于未经证明的漏费或漏成交。

下表金额为元，实际读回见 `lanes.mixed.stages`。

|实际阶段|06-29 现金 / 净资产|06-30 现金 / 净资产|07-01 现金 / 净资产|
|---|---|---|---|
|报告保存前|998,675 / 999,903.80|999,150 / 999,954|999,150 / 999,962.80|
|仅保存报告|998,675 / 999,903.80|999,150 / 999,954|999,150 / 999,962.80|
|明确采用报告|998,600 / 999,828.80|999,075 / 999,879|999,075 / 999,887.80|
|采用后再接入 07-01 成交|998,600 / 999,828.80|999,075 / 999,879|997,070 / 1,001,473.80|

仅保存前后业务投影一致；采用后原股票数量没有重复增加，后续卖出仍正确承接，07-01 新买入也没有改写报告日。另行读回 `auto_reconciled=true`，但财务结论仍由持仓、现金、资产负债和净值勾稽证明，不由标记代替。

本次真实失败也保留：首次报告输入缺少股票必填 `cost_price` 键，服务端拒绝；只读确认同日报告未保存、原有效流水未变后，补足单位成本价再提交。采用成功后，采集器又因把对账列表参数误写为 `resource` 而出现本地 `TypeError`；改为 `resources=[product_id]` 后只读核验，没有重复采用。两项均为调用方错误，不包装成后端失败；诊断见 `lanes.mixed.failures`。

两次恢复证据分别保留：`lanes.mixed.recovery_reports.recovery-1-reports` 只有起点报告；`stages.recovery-1-preflight` 是补报前快照；`stages.recovery-2-preflight` 是采用后的只读恢复快照。二者不能合并成一个“恢复前状态”。采用前报告 ID 对应关系见 `saved_reports` 与脱敏回执，采用状态另见 `adoption_readback`。
