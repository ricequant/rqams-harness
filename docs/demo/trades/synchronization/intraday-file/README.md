# 日内文件同步：第二份完整快照不是追加成交

[返回流水处理场景](../../README.md)

混合数据源产品已经有可读的起始头寸，但托管估值报告晚于交易到达。运营先拿到交易日 D 上午的成交文件，下午又拿到同一交易账户的新版本。目标不是把文件里的行都追加进去，而是让 D 日估值跟随该账户截至最新截点的有效成交，并把还没收到的报告留到[迟到报告校准](../valuation-report/README.md)单独处理。

## 1. 先查已有什么，再选导入方式

先用 [products.get](../../../../products.md#get) 确认当前工作空间内的唯一产品 ID、`data_source=trade_and_valuation_report`、`auto_overwrite`、业务日期和[账户配置](../../../../fields/products.md#productaccount)。读回 D 日前的有效[头寸报表](../../../../balances.md#get)，留存已有现金、证券、份额和净值；从这个起点继续，不因报告迟到重复录入起点资金或已有成交。报告日和 D 日由业务材料确定，不由文件接收时间推定。

先用 [trades.list](../../../../trades.md#list) 按产品、账户检查 D 交易日是否已有结算，不加资产单元筛选：同账户其他单元已有结算，也会拒绝本单元的日内行。再按获准单元核对本次会替换的 `intraday_upload` 或 `open_api` 成交，保留各来源、读全分页。已有结算时转[日内到结算接管](../intraday-and-settlement/README.md)；没有结算也仍须取得实际替换范围授权。

在本例中，第一份文件包含成交 A；下午收到的第二份仍包含 A（可带券商确认的量价修订），还新增收录了 11:00 的成交 B。文件到达时间不是成交时间。第二份是从开盘起、截至它自己截点的完整文件，不是只含 B 的差量。若对方只发了 B 或一张更正通知，先向来源方复原、核对完整文件。只传 B 并不会让系统保留 A：按[日内文件导入规则](../../../../trades.md#upload-intraday-file)，按成功解析的交易日、产品、账户及资产单元，当前有效日内与 OpenAPI 流水会被替换。

## 2. 准备两份文件，逐次核对覆盖范围

- 按已读账户的 `broker` 和账户号码核对文件归属，采用该通道支持的日内成交模板，例如 RQ 通道的日内成交工作簿。不把任意 CSV 改名或改列后当模板。逐行核对实际成交时间、归属交易日、标的、方向、量价、费用与币种；夜盘不能只看成交自然日，基金代码也要核对解析后的后缀。
- 写前用 [trades.download](../../../../trades.md#download) 或完整分页结果，把目标日、账户与已确定的单元范围内现有明细留存到本地；保留原文件、版本和截止时点。第二次上传前再次保存第一次的有效流水与可读头寸，而不是事后依赖能找回被替换明细。
- 逐份确认「产品、账户、交易日集合、资产单元（如有）、允许替换的来源和文件版本」。接口没有独立的日期白名单；文件跨日时，先核对每行实际交易日再决定是否提交。指定单元时先用 [asset_units.get](../../../../asset_units.md#get) 核验归属并传 ID；替换仅匹配该单元，省略参数则仅匹配未绑定单元的旧有效记录。不得把省略理解为替换账户全部单元。

<a id="trade-date-coverage"></a>
### 自然日查询与交易日替换必须分开

`trades.list` 和下载的起止日期按 `datetime` 筛成交自然日，文件替换按 `trading_date` 交易日。本例为股票日盘，两者日期相同；夜盘及跨日成交先按品种交易日历确认 D 交易日可能对应的全部成交自然日，扩大查询范围并读全分页，再筛 `trading_date == D` 核对成交。账户级结算检查不加单元筛选；替换清单再核对目标单元，未绑定单元也要从完整明细中明确识别。只查询 `start_date=end_date=D` 会漏掉此前自然日晚间成交，不能作为完整备份或覆盖前证明。

## 3. 先第一份，再第二份；出现异常先停

以下片段在同一个[已连接的 Python 会话](../../../../connection.md#建立连接)中分阶段执行。`product_id` 取本次已核对产品配置的 `id`；`account` 取已核实账户的 `accounts[].name`，不是券商账号；`trade_date` 是文件归属交易日 D；`asset_unit_id` 是核实后的单元 ID，或在授权覆盖账户范围时用 `None`。`first_file_path` 和 `second_file_path` 是两份已核对的通道文件在本机的实际路径。

```python
first_receipt = rqamsh.trades.upload_intraday_file(
    resource=product_id,
    file_path=first_file_path,
    account=account,
    asset_unit_id=asset_unit_id,
)
```

先留存回执中的 `effect_count`、`err_msg` 及 `confirmation_id`。有凭证 ID 时用 [confirmations.get](../../../../confirmations.md#get) 比对账户、登记日期、解析与登记条数以及逐项结果。第一份应读回截至上午截点的成交 A，不把没有 B 解释成下午无成交。以下查询在每次写入前后使用同一范围；读全分页并核对明细，而非只比较条数：

```python
effective_trades = rqamsh.trades.list(
    resource=product_id,
    start_date=trade_date,
    end_date=trade_date,
    account_names=[account],
    asset_unit_ids=[asset_unit_id] if asset_unit_id is not None else None,
)
```

只有第一份的登记结果与成交明细已经核对、第二份已确认为完整且获准替换，才提交第二份：

```python
second_receipt = rqamsh.trades.upload_intraday_file(
    resource=product_id,
    file_path=second_file_path,
    account=account,
    asset_unit_id=asset_unit_id,
)
```

再查同一范围，应看到第二份里的 A 和 B 按各自量价有效，而不是第一份的 A 再加第二份的 A、B。按[流水字段](../../../../fields/trades.md#trade)对照成交时间、交易日、代码、方向、数量、价格、费用、币种和来源 `intraday_upload`；同一标的可以合法出现多笔，不能只按代码去重。对修订的 A，验证原版本不再计入，不要求替换前后的记录 ID 相同。需要证明范围外没被改时，拿事先留存的相邻日期、其他账户或单元作为对照。

- **部分失败：** [错误详情](../../../../connection.md#item-errors)保留逐行结果。任务正常完成且含逐行错误时，有合法行的交易日仍执行范围替换，只登记该日合法行；没有合法行的交易日不替换。失败行不会保留对应旧成交，客户端部分失败异常不撤销已完成替换。先保存行号、原因、登记数和凭证，重查当前有效流水，再根据原始文件修复。需要修订并获准重传时，重建该范围内的完整正确文件，不要只传失败行，也不要预先手工删除流水。若更正牵涉交易日变化，从旧日和新日同时查证；新文件不含旧日，不能假定旧日自动清理。
- **超时或回执不明：** 保留文件版本、提交时间、账户、业务日、任务标识（如有）和异常详情；有凭证按 ID 查，没有凭证用 [confirmations.list](../../../../confirmations.md#list) 按操作时间找可能匹配的批次，并核对有效流水。一次未查到不证明未写入。未辨明原请求结果前，不连续上传第二份或重发第一份。
- **已结算或超出授权日期：** 保留原诊断并停止日内写入。已结算按券商日终修订处理；涉及封账或其他未获准范围时另行确认，不靠更改日期或账户绕过拒绝。

## 4. 确认估值跟上，并留给报告校准

文件登记与估值完成分开判断。用 [products.compute_state](../../../../products.md#compute_state) 保存当前状态和执行序号，按[未就绪与缺输入](../../../../connection.md#unready-inputs)等待；若要求看到每一版造成的估值变化，应先读回第一版的目标截面，再提交下一版。读取时保留返回的 `date`：过去的 D 日查历史头寸，同时复查受影响的后续日期；若 D 是当天，读单产品实时截面，不用昨天结果顶替。

```python
state = rqamsh.products.compute_state(resource=product_id)
snapshot = rqamsh.balances.get(resource_or_resources=product_id, date=trade_date)
```

从已留存的起点余额推演 A、B 对相关持仓数量、现金和成本的影响。例如，若 A、B 是同一只人民币股票的两笔买入、A 未修订，且期间没有其他业务变动，第二版相对第一版应只增加 B 的数量，并减少 B 的成交额及税费对应的现金；若 A 也修订，则还要计入新版与旧版 A 的差额，不能再计一笔 A。最后用报表实际估值价格核对市值，检查净资产、份额和单位净值的勾稽。成交价不能充当估值价；还有资金或其他事件时先纳入对照，不把净资产变动全归给第二份文件。参见[交易类型影响](../../../../trades.md#transaction-type-effect)与[头寸字段口径](../../../../fields/balances.md#balance-calculation)。

盘中交付应注明成交文件版本和截点：「截至第二份文件所覆盖的时点」，不是「全天成交齐全」。托管报告到达后，按它自己的业务日比较同日头寸；对 `auto_overwrite=false` 的混合产品，保存报告不等于采用。只有在单独授权范围内完成[报告校准](../valuation-report/README.md)，并读回报告日及后续结果，才可宣布估值已按报告校准。这不改变对日内成交完整性的判断。

## 5. 实际短历史验证：第二份保留买入，再加入卖出

本轮在独立教学产品中使用 RQ 通道工作簿，按接收顺序提交人工材料：D 为 2026-06-29，起点是 06-26 明确采用的现金报告；A 为买入平安银行 100 股、10 元，B 为卖出 40 股、12 元。两份日内文件在此模板中未提供费用，不能将其视为已经取得最终佣金。第二份包含 A 与 B 的完整记录，未修改 A 的量价。

实际读回如下，金额为元。原工作簿列、人工行及哈希见[证据](../../evidence.json)的 `lanes.files.files`，回执及头寸见 `lanes.files.receipts`、`lanes.files.stages`。

|实际阶段|当日有效流水|股票数量|持仓成本|现金|当日净资产|次日净资产|
|---|---|---|---|---|---|---|
|第一份日内文件后|1，来源为日内导入|100|1,000|999,000|1,000,024|1,000,005|

成本随卖出和费用按系统口径变化，不直接套用“剩余数量乘原买入价”；本例普通股票的逐笔成本影响见[交易类型规则](../../../../trades.md#transaction-type-effect)。当日估值价与次日估值价不同，不能要求跨日市值不变。随后接入结算的结果见[结算接管案例](../intraday-and-settlement/README.md)。

**验证边界。** 这是历史日期链上的真实受控 SDK 执行，不是自主 Agent 任务或已观测的盘中结果。文件修订 A 的分支、其他券商模板、夜盘、跨币种、资产单元及部分失败未在本次逐项触发；上文保留相应判断，不将其说成已验证成功。
