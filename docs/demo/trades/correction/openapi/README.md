# OpenAPI 流水修改：从一笔错单到估值影响的验证

本例属于[流水修改](../../README.md#correction)场景，处理来源为 `open_api` 的结构化流水。

一笔成交的数量和价格改对了，为什么净资产并不按成交金额等额变化？怎样证明没有改动另一笔成交，也没有改动更正日前的结果？本例围绕这两个问题完成一次历史更正，而不是依次展示流水接口。

**阅读边界。** 资金、成交和“正确成交指令”由测试人员人工设置；产品配置、流水回执、计算状态和头寸来自 2026-11-20 在真实测试部署上的一次受控 SDK 执行。不是客户真实错单，也不是自主 Agent 完成任务的证明。服务端响应的脱敏字段投影保存在同目录 [evidence.json](evidence.json)，正文标出的路径均以该文件为根。示例中的 `<P>`、`<T1>` 等是不可直接提交的别名。

## 1. 问题、材料与证明义务

测试业务请求如下：

> 流水更正教学产品在 2026-06-29 有两笔买入。第一笔实际应为 120 股、成交价 11 元，系统记成了 100 股、10 元；第二笔正确。只改第一笔的数量和价格，费用、账户、日期、来源均不改，并说明当日及后续估值怎样变化。

“应为 120 股、11 元”来自**人工测试指令**（`instruction`），不是从估值差额反推出来的事实。真实业务必须用成交回报、原始文件或用户明确指令核实正确值，不能为凑净值倒算成交。

本次完成需要同时证明：

1. 对象正确：唯一产品、账户、原流水记录均与指令对应。
2. 输入正确：原 ID 保留，只修改获准业务字段，另一笔成交不变，不增加重复成交。
3. 结果可解释：更正日和次日的数量、现金、成本、市值、净资产及净值符合各自口径。
4. 边界明确：更正前的基线未变；验证只覆盖本例实际日期和字段，不外推到所有产品或全部历史。

其中“输入正确”不能代替“结果正确”：流水写入会自动提交必要计算，写入回执不承诺估值已经更新，见[输入变更与重算](../../../../index.md#valuation-recompute)。

## 2. 数据来源：原型、隔离设置与脱敏

本例只读参考了测试环境已有的流水产品，然后**新建一个独立演示产品**，没有在原型上制造错单。按本次创建回执锁定新产品，核对[归属空间](../../../../workspaces.md#use)、配置及[当前身份能否写入](../../../../permissions.md#可见不等于可写)后才操作。

|设置|已有原型的实际配置|演示产品的实际配置|本例这样设置的理由|
|---|---|---|---|
|数据源|`trade_and_valuation_report`|相同|允许流水输入；不把混合产品等同于已采用报告，见[数据源](../../../../fields/products.md#data-source)|
|业务区间|2023-10-11～10-13|2026-06-26～06-30|重新建立短区间，不复制原型持仓或声称日期平移后行情相同|
|账户|一个 RQ 通道交易账户|一个 RQ 通道交易账户，别名“教学交易账户”|流水 `account` 必须匹配产品内账户，见[账户字段](../../../../fields/products.md#productaccount)|
|份额策略|`auto_prev_unit_net_value`|相同|用现金入金建立初始份额，见[份额策略](../../../../fields/products.md#unit-policy)及[份额形成](../../../../fields/balances.md#balance-inputs)|
|自动采用报告|`true`|`false`|演示不上传报告，避免额外覆盖输入；不是关闭原型开关，见[采用规则](../../../../reconciliation.md#valuation-report-overwrite-setting)|
|封账日|`null`|`null`|不存在已配置封账日；仍须按流水写入规则校验，不从名称猜可写|
|日历、产品标签|`exchange`、`paper`|相同|是普通模拟产品，不是模拟交易撮合模板，见[产品字段](../../../../fields/products.md#product)|
|费用配置|`fee_settings={}`|相同|没有配置产品年费；两笔成交的佣金另行显式提供，不将空配置解释成所有业务均免费|

证据：`prototype`、`prototype_compute_state`、`product`。原型只取得配置与计算状态，没有取得它的业务头寸，不能说本例复现了原型的资产或收益。

公开材料采用字段白名单：替换部署内实体的名称、ID 和有效外部流水键，去掉部署地址、用户、空间、账号、无关字段和具体录入时间；保留证券代码、业务日期、成交量价、费用、估值数字与执行序号。**没有缩放金额或平移日期**，因此下文可以逐数复核；这些结果也不再代表其他行情日期。

## 3. 先建立现状，而不是立即写入

### 3.1 产品与初始状态

用 [products.get](../../../../products.md#get) 读取第 2 节的配置。读取与写入的参数都使用实际解析出的产品 ID；目标空间尚不明确时，先按[定位空间与产品](../../../workspace-routing/README.md)处理，本例不重复接入流程。

本例先在 06-26 录入一笔人工资金流水：`transaction_type=cash_in`、`order_book_id=CNY`、`settlement_amount=1000000`，再于 06-29 导入两笔人工买入。`settlement_amount` 是该类型必填的本金输入，不是只读输出 `estimated_delta_cash`，依据见[写入必填字段](../../../../trades.md#transaction-type-write-rules)。入金和成交是**测试准备**，不是发现错单后又补录一份：共三条流水，无报告覆盖、无其他人工业务输入。`cash_in` 增加现金并参与份额形成，不能当作投资收益，依据见[现金交易类型](../../../../trades.md#transaction-type-effect)。

06-26 实际读回：现金及净资产均为 1,000,000 元，份额 1,000,000，单位净值 1.0；持仓只有 `current_deposit`。证据：`before.balances.2026-06-26`。这是更正前的控制点，不用“最近有数据的一天”替代它。

### 3.2 定位两笔买入

先按[流水查询](../../../../trades.md#list)读取已知业务区间，核对 `total` 和分页，再按[单条读取](../../../../trades.md#get)保存命中的记录：

```python
rows = rqamsh.trades.list(
    resource=product_id,
    start_date="2026-06-26",
    end_date="2026-06-30",
)
original = rqamsh.trades.get(resource=product_id, trade_id=t1_id)
```

本次 `total=3`，三条均返回；其中一条为期初入金，两条为下表买入。不是用证券代码单独认定“同一笔”。

|核对字段|T1：需要更正|T2：不更正|
|---|---|---|
|记录 ID|`<T1>`|`<T2>`|
|`foreign_id`|`<外部键-T1>`|`<外部键-T2>`|
|`datetime`|2026-06-29 10:00:00|2026-06-29 10:05:00|
|`trading_date`|2026-06-29|2026-06-29|
|`order_book_id`|`000001.XSHE`|`600036.XSHG`|
|`transaction_type` / `asset_class`|`buy` / `stock`|相同|
|`account` / `source`|教学交易账户 / `open_api`|相同|
|`quantity` × `price`|100 × 10|100 × 20|
|`commission` / `tax` / `other_fees`|5 / 0 / 0|5 / 0 / 0|
|`currency` / `exchange_rate`|`CNY` / 1|相同|
|`estimated_delta_cash`|−1,005|−2,005|

证据：`before.trades`。字段含义见[流水记录](../../../../fields/trades.md#trade)：`datetime` 与 `trading_date` 不是所有品种下都相同；`foreign_id` 是外部业务键，不是 `trade_id`。列表主键为 `_id`，`get` 返回主键为 `id`，更新回执中为 `_id`，使用各端点实际键名，不凭一个示例套所有响应。

### 3.3 取得写前估值

确认 [compute_state](../../../../products.md#compute_state) 为 `normal` 后，读取三天的[历史头寸](../../../../balances.md#get)，保留实际 `date` 与完整平铺持仓：

```python
snapshot = rqamsh.balances.get(
    resource_or_resources=product_id,
    date="2026-06-29",
    fields=["date", "positions", "total_assets", "total_liabilities",
            "total_equity", "units", "unit_net_value", "daily_pnl"],
)
```

06-29 写前现金为 996,990 元：`1,000,000 − (100×10+5) − (100×20+5)`。两只股票估值价分别为 10.24、36.42，市值为 1,024、3,642 元；总负债为 0，净资产为 `996,990+1,024+3,642=1,001,656` 元。这些是**服务端实际读数及本地勾稽**，不是成交指令中的价格，也没有额外向行情源独立核验估值价。

依据：[买入的现金与成本影响](../../../../trades.md#transaction-type-effect)、[估值价格](../../../../fields/balances.md#position-inputs)、[持仓市值](../../../../fields/balances.md#position-calculation)、[净资产](../../../../fields/balances.md#total-equity)。证据：`before.balances.2026-06-29`。

## 4. 从证据选择最小操作

现在才判断“补录”还是“更正”。本例能够排除下列替代解释：

|候选解释|本例证据|结论及下一步|
|---|---|---|
|T1 漏导，应新增|已有唯一命中 T1，且 `get` 可以读回原 ID|不是漏导，不新增第二笔|
|应当同时修改日期、账户或来源|交易日与指令一致；账户和来源按原记录保留，指令未要求更正，也未独立核实其业务正确性|本次不改这些字段，不把授权边界说成业务真伪证明|
|费用导致金额差|三项费用均有明确数值，指令要求费用不变|不能把佣金改成零来凑现金|
|数量和价格录错|T1 为 100×10，测试指令为 120×11|按原 ID 更新这两个字段|
|需要替换券商日内/结算文件|当前是 `open_api` 结构化记录，不是文件批次修订|本任务不上传文件、不删除重导|

本次已确认 T1 的记录 ID，授权只改数量和价格，因此按原 ID 调用 [trades.update](../../../../trades.md#update)，无须为这次局部修改改用 `foreign_id`。普通更新不允许改变交易类型或来源；删除重录会断开原记录 ID，也超出本次授权。持续同步是另一种任务：为每笔外部流水维护稳定、非空的 `foreign_id`，用 [trades.upload](../../../../trades.md#upload) 按产品批量更新或新增，不必逐笔先查 AMS 记录 ID。

若实际业务中没有找到对应的当前有效流水，先核对产品、日期、账户、来源和分页，再与原始成交材料及已有本地备份核对，不把“当前筛选没看到”直接当漏单。涉及文件批次时，用[导入凭证](../../../../confirmations.md#list)按**操作时间**定位批次、查失败行及已登记项，不能按成交日筛凭证后断言没有导入。本例结构化更正没有依赖文件凭证，不额外查询。

## 5. 写前推导：应该变什么，不应该变什么

按[写操作授权](../../../README.md#6-写操作计划卡)，本次授权固定为 `<P>` 内 `<T1>` 的 `quantity:100→120`、`price:10→11`。费用仍为 5/0/0，其他业务字段、T2 和产品配置不改。不提交额外重算，不创建或采用估值报告。

推导以本例人民币普通股票多头为限，且须以读回确认其他输入和同日估值价未变为条件。依据是[买入规则](../../../../trades.md#transaction-type-effect)及[成本、市值和净资产字段](../../../../fields/balances.md#balance-calculation)：

$$
\Delta q = 120-100 = 20
$$

$$
\Delta C = -(120\times11+5)+(100\times10+5)=-320
$$

$$
\Delta \mathrm{Cost}=320,\qquad
\Delta E_d=20\times V_d-320
$$

其中 $C$ 为现金，$E_d$ 为同一业务日更正后的净资产减更正前净资产，$V_d$ 为该日实际估值价。**320 元是额外现金支出和成本，不是净资产损失。** 06-29 的 $V_d=10.24$，预期净资产差为 −115.20 元；06-30 的 $V_d=10.05$，预期差为 −119.00 元。不能拿这两天净资产的跨日差代替同日更正前后差。

历史输入更正会向后传递，到本例到期日 06-30 为止，机制见[重算起点、传播与封账限制](../../../../index.md#valuation-recompute)。06-26 的控制点应保留原结果；06-29 与06-30 都要读回，只检查更正当天不足以证明后续影响。这里没有新增入金或份额事件，因此还应确认两侧份额均保持 1,000,000，再按[单位净值定义](../../../../fields/balances.md#unit-net-value)核验。

## 6. 执行一次，区分回执、计算状态与独立读回

确认对象与授权后，实际只发送一次局部更新：

```python
result = rqamsh.trades.update(
    resource=product_id,
    trade_id=t1_id,
    data={"quantity": 120, "price": 11.0},
)
```

实际回执的必要字段投影：

```json
{"effect_count":1,"updated":{"_id":"<T1>","quantity":120,"price":11,"commission":5,"tax":0,"other_fees":0,"estimated_delta_cash":-1325}}
```

回执先证明 T1 已按原 ID 保存。服务端刷新了 `inserted_datetime`，并将 `estimated_delta_cash` 从 −1,005 重新计算为 −1,325。这两个字段是服务端生成值，不能写入，也不能为了声称“其他字段不变”而忽略它们。字段性质见[流水字段](../../../../fields/trades.md#trade)；证据：`update`。

计算状态实际经历：写前 `normal/execution_id=3`；更新后读到 `computing/4`，随后 `normal/4`。证据：`compute_observations`。本次从开始等待起限定 240 秒，每次只查状态，进入正常后读回目标结果；没有因计算中再次发送更新或重算。状态 API 自身不等待，执行序号也不证明财务数值正确，依据见[计算状态](../../../../products.md#compute_state)及[等待与未就绪](../../../../connection.md#unready-inputs)。

本次实际顺序是：更新回执 → 等到 `normal/4` → 独立 `get` 两条流水并 `list` 同一区间 → 读取三日头寸。独立读回确认 T1 原 ID 保留，其他业务字段不变；T2 完整记录不变，总数仍为三条。公开 `after.trades` 是列表字段投影；完整 `get` 对象的键集合及变动键比较结果另列在 `offline_comparisons`，它是离线核验摘要，不是服务端回执字段，也不等于公开了完整记录。

## 7. 结果：逐项检验写前预期

下表均为同一业务日的写前→写后，金额单位元；正文按金额展示，完整原始浮点表示保留在 `before.balances`、`after.balances`，没有为勾稽改写响应。

|检验项|06-26：更正前基线|06-29：更正日|06-30：后续日|
|---|---|---|---|
|T1 对应持仓数量|没有该仓|100→120|100→120|
|T1 对应持仓成本|没有该仓|1,005→1,325|1,005→1,325|
|T1 对应估值价|不适用|10.24→10.24|10.05→10.05|
|T1 对应市值|没有该仓|1,024→1,228.80|1,005→1,206|
|现金 `current_deposit`|1,000,000→1,000,000|996,990→996,670|996,990→996,670|
|T2 对应数量 / 成本|没有该仓|100 / 2,005，均不变|100 / 2,005，均不变|
|T2 对应市值|没有该仓|3,642→3,642|3,550→3,550|
|总负债|0→0|0→0|0→0|
|净资产|1,000,000→1,000,000|1,001,656→1,001,540.80|1,001,545→1,001,426|
|同日净资产差|0|−115.20|−119.00|
|份额|1,000,000→1,000,000|相同|相同|
|单位净值|1.0→1.0|1.001656→1.0015408|1.001545→1.001426|

三条检验链可以复核结论：

- **现金与成本链：** 两个受影响日现金均少 320，目标仓成本均多 320；佣金没有被重置。不是为了得到某个净资产而另写现金调整。
- **估值链：** 06-29 净资产为 `996,670+1,228.80+3,642=1,001,540.80`；06-30 为 `996,670+1,206+3,550=1,001,426`。两日分别满足第 5 节的差额公式，份额不变，单位净值等于各自净资产除以份额。不能由此推断所有产品收益公式均已验证。
- **控制链：** 内部完整读回比较确认 06-26 所请求结果、T2 成交记录及产品配置不变；公开材料提供必要字段投影，并以 `offline_comparisons` 列出后两项的键集合与变动键比较摘要。T2 持仓数量、成本、估值价、市值不变。此处比较的是同日写前后，不能要求不同日期行情市值不变。

“另一笔不变”也不等于它的所有派生指标不变。T2 对应持仓 `weight` 随净资产分母变化，这一关系已复核；`contribute_returns` 也实际改变，但**本次历史返回不能由所引字段页简式复现，差异原因未核实**。例如 06-29 两侧 T2 的 `daily_pnl` 都为 1,637，上一估值日净资产均为 1,000,000，按[收益贡献字段](../../../../fields/balances.md#position-calculation)简式均应为 0.001637，实际分别约为 0.001680495 和 0.001593653。材料在 `non_target_derived_changes` 保留了对应输入与返回；不推断服务端算法，不将这项算作通过，也不因此否定前述现金、市值与净资产的独立勾稽。

## 8. 业务交付：回答原请求，而不是报告接口成功

> 已在流水更正教学产品的教学交易账户中，将 06-29 10:00 的 T1 按原记录 ID 从 100 股、10 元更正为 120 股、11 元；佣金仍为 5 元，日期、账户和来源未变，另一笔成交记录未变，未新增重复成交。
>
> 自动估值更新后，06-29 与 06-30 的目标持仓均增加 20 股、现金均减少 320 元。按各日实际估值价 10.24 和 10.05 元，同日净资产分别下降 115.20 和 119.00 元，与读回结果一致；不是净资产下降 320 元。份额仍为 1,000,000，单位净值分别变为 1.0015408、1.001426。06-26 基线未变，产品配置和另一证券同日的数量、成本、市值未变。
>
> 该结论覆盖本例三个日期及上述字段。证券估值价取自服务端结果，未独立审计上游行情；没有证明全部中间日期、所有派生收益指标或其他品种均正确。测试产品保留供审核，没有修改原型或删除资源。

这是基于本次实测材料的脱敏答复，不是对读者所在环境的操作授权或既有结果承诺。

## 9. 条件改变时，沿同一证明义务处理

以下是契约分支，**本次没有逐一触发**，不写成实测成功。

|条件变化|为什么不能沿用主线|所需证据与动作|
|---|---|---|
|记录已与正确值一致，或更新返回 `effect_count=0`|零修改不等于不存在|[get](../../../../trades.md#get) 核对同一 ID；一致则无需写入，不一致则查[更新结果](../../../../trades.md#update)，不删除重导|
|请求超时、断连，未收到回执|客户端未收到不证明服务端未写入|保留目标、原 ID 和已提交字段；按原 ID 只读查证，未确认前不重发。若无回执就不要求提供不存在的回执 ID，见[写入结果](../../../../connection.md#write-result)|
|确证漏单，而不是已有记录错误|没有可更新的原 ID|按 [upload](../../../../trades.md#upload) 准备真实成交及稳定外部键，逐项检查结果；发生[部分失败](../../../../connection.md#item-errors)时核实已落库项，不整批盲目重传|
|来源是日内或日终文件，需修订整批|文件是日期/账户等范围替换，不是单行追加|先保留当前有效记录和批次材料，再按[日内](../../../../trades.md#upload-intraday-file)或[日终](../../../../trades.md#upload-settlement-file)规则取得覆盖授权；不把本例单笔方案当所有文件的修复方法|
|正确日期也变了|旧、新日期都有影响，且超出主线仅改量价的授权|先确认新日期与扩大后的授权；按 [update](../../../../trades.md#update) 用 `datetime` 表达日期更正，不直接写 `trading_date`；量价也错时一并提交已获准字段，再核对旧、新日期及后续链|
|计算 `error`、未知状态或等待超时|输入落库和估值就绪是两层|保留记录及最后状态，按[未就绪规则](../../../../connection.md#unready-inputs)报告已确认与未确认项；不把超时当服务端取消，不追加写入|
|封账、报告覆盖、权益事件或其他输入也变了|第 5 节的简化条件不再成立|回到[估值链与重算边界](../../../../index.md#valuation-recompute)，先核实输入及授权；不删掉差异字段来通过核验|

## 10. 供其他案例引用的边界

本例独立维护“流水怎样查证、为何选择更正、怎样验证影响”，不在对账或收益案例重写一套：

- 对账发现数量差，先按[数量差异追溯](../../../reconciliation-controls/README.md#41-数量不一致沿历史持仓追到错误源头)确认根因及原业务日；确需处理流水后引用本例的[现状取证](#read-current-state)、[操作选择](#choose-write-path)、[影响推导](#correction-effect)和[估值复核](#verify-valuation)。本例不判定托管报告哪一边权威。
- 收益异常追到错单，引用上述更正步骤；区间基点、分红和收益率先按[区间核对五项](../../../returns-diagnosis/README.md#区间核对五项)处理，不拿本例现金差代替收益率。
- 估值报告保存和采用仍看[保存、解析、采用、就绪的区分](../../../valuation-report-reconciliation/README.md#第-4-步保存解析采用就绪是四层)，不为修流水擅自采用报告。

### 证据核验与复现限制

[evidence.json](evidence.json) 是可离线审读的脱敏材料，不是 API 契约或可直接提交的输入。材料保留实际持仓行和本例核对所需字段，可用于复核记录、配置和财务数值；前述收益贡献差异仍未解释，估值价也未向独立行情源核验。

同目录 [run.py](run.py) 是既有的可选受控脚本：创建模拟交易模板产品、导入和更正构造流水并清理自有对象。它与本次“普通模拟产品、入金建份额、保留产品”的执行配置不同，**不是 evidence.json 的生成器**，也不覆盖本页全部分支。阅读本例不要求执行它；运行前必须单独核对其副作用与授权。本轮未修改或执行该脚本。
