# 首次接入：已有完整历史流水，怎样建立并接续头寸链

用户已经在外部系统运行产品，现在第一次接入 AMS。要解决的不是“文件上传了吗”，而是：**从哪个真实状态开始，历史是否重建正确，下一笔成交能否接上。** 本例先处理纯流水产品，再给出混合产品及文件材料的分支。

## 1. 从用户的历史材料确定交付

教学业务由人工设定：产品从 2026-06-26 开始，人民币资金入账，之后有股票买卖；外部系统保留稳定成交编号。首次同步截止 06-30，完成历史核验后接入 07-01 的新成交。不复制已有客户产品或凭净值差反推成交。

|历史材料|本例内容|用来证明什么|
|---|---|---|
|起始状态|此前无资产负债，06-26 入金 1,000,000 元，无其他份额事件|起点来自测试指令，而不是把未知初仓当零|
|第一笔成交|06-29 买入 `000001.XSHE`，100 股、10 元，佣金 5 元|历史首批记录；后续会收到上游修订|
|第二笔成交|06-30 卖出同一股票，40 股、12 元，佣金 5 元|历史不是单日静态持仓，还要处理卖出和日期承接|
|外部标识|入金、买入、卖出各有稳定且不同的 `foreign_id`|支持查证、修订与重复发送，不以证券代码代替成交身份|

真实业务先盘点资金进出、持仓、负债、费用、份额及权益事项。**拥有全部成交，不必然拥有重建净值所需的全部输入。** 逐项确认哪些由系统自动处理、哪些需要提供，避免既漏记又重复录入自动权益；具体品种见[交易及权益影响](../../../trades.md#transaction-type-effect)。缺少必要材料时，指出受影响日期和结果，不补零或写调平流水。

## 2. 从真实起点建账，不把今天的余额搬回历史

本例创建独立普通模拟产品，显式采用 `data_source=trade`、`unit_policy=auto_prev_unit_net_value`，起始日为 06-26；教学验收截止 07-01，产品到期日也限定在该日。产品创建与账户配置见[创建产品](../../../products.md#create)及[账户字段](../../../fields/products.md#productaccount)。创建后保存返回的产品 ID，读取配置并核对空间、账户和当前写权限，再只向该产品写入。

这里的普通模拟产品不等于[模拟交易撮合模板](../../../paper_trading.md)。外部策略已经产生成交时，本例同步的是成交结果，不再上传一份模拟信号令系统重复撮合。

两种历史起点不能混用：

- **确实拥有从业务开始起的完整材料：** 建立真实期初状态，再应用其后的所有变动。本例起点为无持仓的资金入账，不能将末日余额当作期初资金。
- **只能从中途可信截面开始：** 以完整日末截面建立适合产品数据源的起点，从该日之后的业务变动接续，不再应用已包含的历史成交。报告和产品持仓表按日覆盖，不提供“上午截面接下午成交”的切点：同日流水先应用，随后会被该日截面覆盖。只有盘中截面时，先补齐可信日末状态，或从更早可信日末重建，不能仅排除上午成交后上传下午成交。本分支不声称恢复更早完整历史，报告初始化见[报告采用规则](../../../reconciliation.md#valuation-report-overwrite-setting)。

资金入账与份额形成不是投资收益；本例使用现金流水和自动份额，业务选择依据见[份额策略](../../../fields/products.md#unit-policy)。有存量资产、负债或分类份额的产品，不能照抄本例的单笔入金起点。

## 3. 首次上传：把历史业务身份一起带入

下列是本例的结构化材料形状。`product_id`、`account` 来自已核对的新建对象；尖括号外部键是不可直接提交的脱敏别名，实际执行须替换为上游稳定编号，不能每次随机生成新键。

```python
seed = {
    "datetime": "2026-06-26 09:30:00", "transaction_type": "cash_in",
    "asset_class": "current_deposit", "order_book_id": "CNY",
    "settlement_amount": 1000000, "account": account,
    "foreign_id": "<外部键-history-3>", "commission": 0, "tax": 0, "other_fees": 0,
}
buy = {
    "datetime": "2026-06-29 10:00:00", "transaction_type": "buy",
    "asset_class": "stock", "order_book_id": "000001.XSHE",
    "quantity": 100, "price": 10, "commission": 5, "tax": 0, "other_fees": 0,
    "currency": "CNY", "exchange_rate": 1, "account": account,
    "foreign_id": "<外部键-history-2>",
}
sell = dict(buy, datetime="2026-06-30 10:00:00", transaction_type="sell",
            quantity=40, price=12, foreign_id="<外部键-history-1>")
receipt = rqamsh.trades.upload(resource=product_id, data=[seed, buy, sell])
```

`cash_in` 用 `settlement_amount` 表达本金，`estimated_delta_cash` 是输出，不作为输入；普通股票填不复权实际成交价。逐项结果与输入顺序对应，按错误容器判断成功，不能只看 HTTP 状态或返回长度。字段与校验以[结构化上传](../../../trades.md#upload)为准。

大区间可以由调用方按业务日期、账户组织批次，记录每批材料、回执和确认范围；SDK 不自动拆批，也不要求为每个自然日发一个请求。发生部分失败时，先查哪些已保存；无回执的超时也先只读查证，不立即重复整批。整个历史尚未导完时，不把中间头寸作为完整交付。

若用户拿到的是历史文件，先识别支持的券商模板及其日期、账户和资产单元范围，再选择[日内文件](../synchronization/intraday-file/README.md)或[结算文件](../synchronization/settlement-file/README.md)。同日同范围的完整文件不能任意拆成“每份追加一部分”；后一次范围替换可能移除前次有效记录。一个文件包含哪些日期，以实际解析的合法行和逐行错误为准，不凭文件名判断。

## 4. 检查历史链：先验证输入，再验证每个关键截面

按原历史范围读取[流水](../../../trades.md#list)，核对 `total`、完整分页、外部键、日期、量价、费用和账户；本例首次应有入金及两笔成交。然后按[估值就绪规则](../../../connection.md#unready-inputs)等待自动计算，读取各检查点的实际日期，不另交手动重算。

|检查点|先推导的数量和现金|结果核验|
|---|---|---|
|06-26 起点|现金与净资产 1,000,000；无股票|核对现金、负债、份额和单位净值|
|06-29 首次买入后|100 股；现金 `1000000−100×10−5=998995`|成本包括佣金；市值按当日估值价而非成交价|
|06-30 卖出后|60 股；现金 `998995+40×12−5=999470`|核对卖出、剩余持仓、净资产与份额|

这些金额是人工输入的预期，必须和读回逐项比对。证券行情、权益和汇率涉及的上游完整性不能仅凭本地勾稽证明。[净资产、持仓市值及单位净值口径](../../../fields/balances.md#balance-calculation)用于核验，不用单位净值环比代替收益率。

长历史选择初始日、资金/权益变动日、月末和截止日等独立检查点，并说明未核验的中间日期。最终一天一致不证明中间历史正确；产品无成交的日期仍有[逐日估值承接](../../../index.md#valuation-lifecycle)。

## 5. 核验发现上游历史修订：直接用稳定外部键同步

随后上游明确修订 06-29 买入为 120 股、11 元，佣金不变，并补来一笔 06-30 买入 `600036.XSHG`、100 股、20 元、佣金 5 元。这是新的外部业务材料，不是为了让净值好看而倒算。

```python
corrected_buy = dict(buy, quantity=120, price=11)
additional = dict(buy, datetime="2026-06-30 10:00:00",
                  order_book_id="600036.XSHG", quantity=100, price=20,
                  foreign_id="<外部键-history-4>")
current_history = [seed, corrected_buy, sell, additional]
receipt = rqamsh.trades.upload(resource=product_id, data=current_history)
```

调用方可以直接同步这一批完整业务记录：已有非空 `foreign_id` 的更新，新增键的插入，不需要先逐笔查询 AMS ID 并筛出要改的成交。**匹配范围是同产品，不按账户分别隔离外部键**；上游编号若跨账户或系统重复，应事先建立稳定命名空间。此操作不是局部补丁，完整业务字段和费用都要核对；未出现在本次批次中的旧记录不会因此删除。

写后核验目标买入已修订、卖出未改、补来成交只新增一次。06-26 应保持不变；06-29 现金减少 320 元，股票增加 20 股；06-30 还要计入补来的第二证券，不能把所有净资产变化都归到那 320 元。按实际估值价重新核验成本、市值、净资产及后续日期。

本例随后有意重发同一批 `current_history`。**预期是更新原记录、不新增重复成交，但仍重新提交计算，而不是跳过请求。** 前提是同产品、各笔非空外部键稳定且不冲突、完整业务内容相同，并且各项校验成功；规则见[结构化上传](../../../trades.md#upload)。本次实测重发前后四条流水的记录 ID、全部检查点的持仓、现金、净资产和单位净值一致；计算批次却从 `execution_id=2` 变为 `3`，并观察到 `computing` 后恢复 `normal`，证明重发确实触发了新一轮计算。

这一步用于验证重复投递不会重复记账，不是要求每次查询结果都重发输入，也不能用重发代替等待计算。缺少稳定外部键时，成功的重复提交会按新记录插入并重复记账，不能照抄该步骤。撤销成交要查明实际记录并获准删除，不能靠上传列表缺一项表达撤销。

## 6. 历史截止后接入增量，证明以后能够继续维护

历史确认到 06-30 后，07-01 再收到一笔 `000001.XSHE` 卖出 20 股、12 元、佣金 5 元，使用新的稳定外部键上传。核对它只新增一次，并从已修订历史继续：该证券剩余 60 股，另一证券仍为 100 股，现金再增加 235 元；07-01 以前已核验结果不应被这笔未来业务改变。

历史与增量应记录各自覆盖的业务日期及上游游标/版本。游标推进不能只看“请求已发送”；要依据确认成功的输入。交界处有重叠时用稳定身份核验不重复，有缺口或迟到修订时回补实际业务日，不将到达时间误写为交易日。

后续按[OpenAPI 持续同步](../synchronization/openapi/README.md)维护，不必每天全量重传历史。混合产品拥有历史报告时，先核验流水重建结果，再按[迟到报告校准](../synchronization/valuation-report/README.md)采用；报告对上不能替代历史成交核验。

## 7. 交付与证据边界

交付应同时给出历史覆盖区间、账户、实际有效记录、关键日期核验、已修订项和增量接续结果。输入登记完成、估值就绪、业务核验通过分别判断；存在失败行或缺失事件时，不用“产品已经创建”结束任务。

本轮受控 SDK 执行的实际结果如下，金额为元。证券估值价直接取服务端同日返回，未独立审计上游行情；各阶段明细、完整检查点及字段投影见 `lanes.history.stages`。

|实际阶段与业务日|有效流水总数（全测试区间）|平安银行数量|招商银行数量|现金|净资产|
|---|---|---|---|---|---|
|首次历史导入，06-29|3|100|无持仓|998,995|1,000,019|
|首次历史导入，06-30|3|60|无持仓|999,470|1,000,073|
|批量修订并补录，06-29|4|120|无持仓|998,675|999,903.80|
|批量修订并补录，06-30|4|80|100|997,145|1,001,499|

|接入新成交，07-01|5|60|100|997,380|1,001,580.60|

重发前后的公开业务投影一致，逐项回执返回相同记录 ID；可分别核对 `lanes.history.inputs`、`receipts.batch-upsert` / `batch-repeat` 及 `stages.corrected` / `repeated`。`compute_observations` 中对应阶段的计算批次为 2 和 3：业务没有重复，计算仍再次执行。后续新成交没有改变此前检查点，06-26 起点在各阶段均保持不变。表中“无持仓”依据完整持仓集合，不是将未返回字段补零；总数包含全区间已导入记录，不是当天成交笔数。

本页的入金、成交和修订均为人工教学材料，不是客户真实流水；受控 SDK 证据统一见[场景证据](../evidence.json)，不能把它说成自主 Agent 已执行上述所有诊断分支。中途非现金截面初始化、撤销成交、大区间分批和其他品种仍按各自契约处理，不因本例普通股票通过就宣称全部历史均可原样恢复。

首次采集在产品创建后因采集器误要求纯流水产品返回 `auto_overwrite=false` 而停止，实际该字段为 `null`；当时未提交业务输入。保留原失败后，恢复时复用原创建回执并重新核验所有权，没有重复创建。该开关只在混合产品报告采用的场景有意义，不以此改写纯流水产品配置。
