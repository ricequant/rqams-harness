# 对账：从差异定位到业务修正

用户说：“帮我把示例产品 10 月 28 日的账核一下，没对上的地方看怎么处理。”

这不是“依次调用所有对账 API”。Agent 要先建立可靠的比较对象，分清已有状态，再沿历史状态、业务输入和外部事实追溯差异的形成过程，决定是否需要写入，最后证明处理结果。**对账目标是找到并解释根因；修复发生在错误的源头，不是把对账当天的数字补平。** 已确认的估值口径差异可以解释给用户，不一定需要修改数据。

下文用虚构产品“示例产品”、业务日 `2026-10-28` 和构造金额说明判断。各小节的观察是条件分支，不是某个环境的真实回执，也不是要求逐条制造这些差异。

## 1. 找到同一空间、同一产品、同一业务日

先按[空间与产品定位](../workspace-routing/README.md)确认部署、成员空间和产品唯一 ID，后续调用固定使用这个 ID，不在不同空间按同名产品拼接数据。若用户只说“昨天”，先按业务时区确定具体日期，并核对它是否为用户要求的估值日；不自动把自然日改成上一交易日。

用 `products.get` 读配置，带着下面的问题看，而不是把整份 JSON 发给用户：

- 用户要求核对哪一天，截止到哪一天？是否涉及封账、产品开始日或交易开始日？不要擅自换成“最近一天”。
- `data_source` 是交易流水、纯估值表还是混合？`auto_overwrite` 如何配置？不同模式下，报告导入后的作用不同。
- `accounts`、资产单元和份额配置是什么？差异是否属于某个账户、单元或分类份额？
- 当前身份是否有对账所需权限？对账的查询操作也要求目标产品 `write`；仅有净值读取权限不足以执行差异核对。

**分支边界：** `reconciliation.diff` 仅支持 `trade_and_valuation_report` 混合产品。纯估值表产品应核对报告来源、解析与采用后的头寸，不能套用混合产品差异接口；也不为方便核对擅自修改产品数据源。详见[产品配置](../../products.md#get)、[对账调用约定](../../reconciliation.md#api-使用约定)。

## 2. 先读状态，分清“已标记”和“已采用报告”

用 `reconciliation.list(resources=[product_id], start_date=..., end_date=...)` 查看目标日，结合产品配置与报告记录判断。这里的 `product_id` 表示前一步实际解析出的 ID，不是示例中的可直接提交字符串。

|观察|含义与下一步|
|---|---|
|`done=false`|当前未标为完成；先查缺件和具体差异，不直接调用 `auto`|
|`done=true`、`auto_reconciled=false`|有完成标记，但该日当前没有估值表覆盖；查看备注并核实依据，不能仅凭标志宣称已核对无误|
|`auto_reconciled=true`|当前存在估值表覆盖；结合数据源、覆盖配置及可用操作记录解释来源，不能据此断言是人工执行了 `auto`|
|当前已采用估值表，用户只要求核实采用情况|核对实际报告与头寸，明确结论是“已采用报告”，而不是“原始流水逐项一致”|
|当前已采用估值表，但用户要检查流水是否完整|覆盖后的结果不是独立的流水正确性证据；继续查原始业务材料和流水。若要撤销覆盖恢复独立比较，先说明影响并单独取得授权|
|目标日状态缺失或返回区间为空|确认日期、产品范围与头寸是否具备，不把缺项解释成已对齐|

覆盖可能由报告导入、配置变更或显式自动对账产生；`auto_overwrite=false` 也不能证明历史覆盖不存在。人工完成标记会被后续覆盖写入或撤销改写。具体规则见[估值表采用设置](../../reconciliation.md#valuation-report-overwrite-setting)、[对账状态](../../reconciliation.md#list)。

## 3. 没有参照资料，就先补件，不急着比较

用 `valuation_reports.list(resource=product_id, start_date=date, end_date=date)` 核对目标日报告，同时看对账状态中的缺件提示。

- **没有该日估值表：** 获取正确产品、正确日期的材料，按[估值表导入案例](../valuation-report-reconciliation/README.md)检查模板、已有报告与写入影响；取得授权后导入，再读回报告与状态。没有文件或解析失败时，结论是“缺少有效参照，暂不能完成对账”，不是“无差异”。
- **已有报告：** 核对日期、产品和解析内容；内容有误应先更正参照资料，不用错误估值表倒推修改 AMS。是否替换需限定日期与授权。
- **缺资产单元持仓单：** 只有产品确有相关单元时才核对该单元、日期与持仓单。用 `positions_statements.list` 查材料，按[资产单元持仓单与数量对账](../../positions_statements.md)继续；产品估值表与资产单元持仓单不是可互换的输入。

**上传并非无副作用的“补附件”。** 纯估值表产品以及启用自动覆盖的混合产品，导入报告可能改变估值；导入前就要读配置并说明影响，不等写完才发现自动覆盖。不要为保留比较基线擅自切换全局覆盖设置，该设置可能影响已保存报告。

## 4. 读具体差异，先解释原因，再决定修什么

混合产品有有效当日报告且计算可用后，调用 `reconciliation.diff`，一次取需要的差异组。先查 `products.compute_state`；计算中按[等待规则](../../connection.md#unready-inputs)有界等待，失败先诊断，不能把失败或旧结果当作无差异。

```python
# 前提：rqamsh 已连接授权空间；product_id 和 date 来自已核实目标。
comparison = rqamsh.reconciliation.diff(
    resource=product_id,
    date=date,
    fields=["positions", "prices", "cash", "receivable", "payable", "net_asset"],
)
```

有分类份额时按需加 `shares_payable`；有资产单元时，另用 `asset_unit_diff` / `positions_statement` 核对单元数量。返回是两个来源的对照，需读明细，不把存在一行就当成已定位错误，也不把某一组为空推广到全部项目。

下面按依赖关系排查；某一步修正后，重新读取差异，原先现金或净值差可能已经随之消失。

### 4.1 数量不一致：沿历史持仓追到错误源头

假设目标日估值表显示某证券数量为 120，AMS 为 100。差额只说明两边结果不同，不能据此认定当天漏了一笔 20 的买入。先按同一品种、代码和多空方向对齐，再查这一数量的形成过程；完整来源见[持仓数量字段](../../fields/balances.md#position)，不要只看买卖成交，忽略初始化、划转、送股、拆分、换股、行权到期或报告覆盖。

**先分清期初就有差异，还是当日新产生差异。**

1. 用 `balances.get` 读取目标日及实际承接的上一估值状态，用对应日期估值表或其他可靠持仓材料核对前序数量。“上一状态”不机械等同于上一自然日或上一交易日。
2. 用 `trades.list` 核对该期间实际生效的流水，逐项看代码、品种、方向、账户、资产单元、数量、业务日期和来源；同时核对该证券的权益等非买卖变化。当天买卖都完整，也不能证明期初持仓正确。
3. 若前序数量已经不同，继续向前查，直到能用证据建立本次核查的可靠起点，再按时间顺序核对它到目标日之间的变化。若前序数量已核实、当日才出现分歧，重点查当日输入和生效过程。差异可能消失后再次出现，不能假设它随时间单调变化；一次数量相等或 `done=true` 都不能独立证明历史正确。
4. 把“首次观察到分歧的日期”和“已证实的根因”分开。前者缩小排查区间，后者必须有业务材料、导入记录或计算证据支持。缺前序报告不代表前序无差异，可继续查可得流水、权益及用户资料；无法建立可靠基线时，交付已追溯到哪里、缺什么证据，不宣称查明根因。

下面是三日**构造教学材料**：同一证券无送股、拆分等其他数量变化，材料中的两笔买入均有独立的构造成交记录，不是按对账差额反推的成交。

|业务日|AMS 数量|参照数量|核查当日输入与承接状态|
|---|---:|---:|---|
|10 月 26 日|80|80|初始化截面及其来源已核实，作为本例起点；不据此推广到更早历史或其他标的|
|10 月 27 日|80|100|成交材料记载买入 20，AMS 未见对应有效流水，需要查明是否漏导、失败或映射到错误对象|
|10 月 28 日|100|120|当日买入 20 在两侧都已记录，数量差异从前序状态延续|

这里要继续验证 27 日成交为何没有进入计算，而不是在 28 日补一笔差额买入。必要时用 `confirmations.list` 定位导入批次，再用 `confirmations.get(status='failed', ...)` 追查失败行；凭证列表按操作时间过滤，不是按成交业务日期过滤，历史补导须同时核对批次时间与行内日期。未落库、落到错误日期或标的、落库但未正确生效是不同原因，不能把“没有找到”直接写成“已确认漏导”。

- 凭证及完整查询证明 27 日成交漏录：按[历史流水更正案例](../historical-trade-correction/README.md)核对重复、来源与写入规则，授权后补到 **27 日**，不是对账日。
- 原成交数量、日期或标的错误：核对实际记录 ID、允许修改字段及原始材料，精确更正；不能保留错误记录再新增一笔完整成交。
- 估值表标的映射、方向或数量错误：更正参照资料，不反向修改正确流水。
- 差异属于资产单元：沿该单元的底层持仓、持仓单及相关变化追查，不默认用母产品普通成交修复。
- 历史中出现报告或持仓表覆盖：这是持仓来源切换点。核实覆盖截面及其依据，可以确定后续计算起点，但不能用覆盖后的相等证明更早流水正确，也不未经授权撤销覆盖。
- 只有数量差、没有业务证据：保留待核实结论，不按差额编造成交；覆盖产生的影子流水也不是真实成交凭证。

根因确认后，从错误实际发生日起复查到用户要求的截止日。历史补录还会改变现金、费用、成本和后续估值；先看这些项目是否随正确重算自然恢复，不能再照修正前的现金差额重复调整。

#### 权益分支：核对事件事实、持仓基数与生效时点

如果异常日附近有证券分红、送股、拆分或换股，先沿[权益来源与在途字段](../../fields/balances.md#in-transit-fields)核对外部事实，再检查 AMS 采用和计算的过程：

- 事件是否实际发生，金额或比例是什么，登记日、除权除息日、到账或生效日分别是哪天；不把这些日期当成同一天。
- 事件所需的登记日或其他规定时点持仓是否正确。若基数已错，继续追该历史持仓，不用当前数量直接反推应得权益。
- AMS 是否登记了应收或数量在途，是否已经到账、生成相应自动权益流水；日终在途为空不代表权益从未发生。
- 是否已有手工权益记录、自动权益处理被跳过，或同一事实被重复维护。不能看到数量差就另补买入，也不能看到现金差就再记一次分红。

证券分红不是产品向投资者分红；先按证券权益来源核查，不能用产品托管分红事件替代。若事件、基数和输入均已核实，但结果仍不符，保留标的、日期、事件、前后状态与计算诊断，报告待查计算或数据采用问题，不用调整项掩盖。

<a id="external-source-check"></a>
#### 外部事实核验：有条件用 RQData，也查用户材料与公开来源

外部核验服务于正在追查的具体问题，不先漫无范围抓行情。先从[头寸公允价及权益字段](../../fields/balances.md#position-inputs)和 [RQData 调用来源](../../rqdata.md#rqdata-calls)确定相应品种实际需要的调用、日期与口径。

|可用来源|如何使用及证据边界|
|---|---|
|用户环境允许的 `rqdatac`|具备相应 skill、按其方式通过许可证验证且有目标数据权限后，查询对应证券的行情或权益。不能只凭安装了包或 AMS 能取到行情，就认定当前 Agent 可直连 RQData；验证失败时记录限制，继续其他可达核验|
|用户提供的材料|成交回报、交割单、托管持仓、权益通知及估值依据用于核实该产品的实际业务；先检查产品、代码、日期、完整性及口径。构造例子的材料明确标为教学用途，不冒充真实凭证|
|公告与财经网站|可访问时用交易所、上市公司、基金公告，以及东方财富等财经网站补充、交叉核验；保留具体来源、所涉日期和数据口径，不以一张未标日期的截图或最新报价代替历史事实|

核验记录区分证券与市场、业务日期与查询时间，以及价格字段、币种、复权方式或权益日期和比例。同源 RQData 查询可帮助检查采用与计算，但不是独立佐证；本次查到的数据也可能已修订，不能冒称就是服务端历史计算时使用的版本。资料冲突时先解释差别和证据缺口，不自动选一个来源覆盖 AMS。

### 4.2 价格不一致：先用产品设置解释口径，再追实际数据

数量相同而市值不同，不一定缺成交，也不一定有错误。先读 `products.get` 中的[估值口径配置](../../fields/products.md#valuationsettings)：期货期权看 `valuation_settings.fut_opt`，ETF 看 `valuation_settings.etf`；同时读差异的 `price.field`，区分人民币价格与结算币种价格，再核对报告的估值依据。

例如产品明确按期货结算价估值，报告明确采用收盘价，且同一合约同一日期的行情证明两侧各自对应这两种价格，就可以向用户解释：“本次价格差来自估值口径不同，AMS 按该产品的结算价设置计算，报告采用收盘价。”这是有证据支持的差异原因，不必先改价格或配置；是否统一口径由用户决定，解释清楚不等于自动获准标记完成。ETF 的收盘价与 IOPV 也应按实际设置判断。

设置说明预期口径，还须确认当日实际是否命中人工公允价、采用报告或进入缺价回退分支，不能只看到一个设置就断言根因。按[公允价来源字段](../../fields/balances.md#position-inputs)追到实际价格，必要时按[外部事实核验](#external-source-check)查询对应行情，核对日期、市场、日终或实时、币种、汇率和复权方式；不统一拿网站最新价或 `close` 比较所有品种。

若设置与实际来源均已核实、同口径数据仍不一致，再区分参照资料错误、人工价格维护错误、源数据修订或计算采用问题。若业务确需维护指定公允价，授权后按[公允价维护](../../custom_instruments.md#insert_fairvalues)处理；不能为了消除差异把成交价写成估值价，也不能因为港股价格数值不同就调整现金。差异返回口径见[价格差异结构](../../reconciliation.md#diff)。

### 4.3 现金、应收或应付不一致：真实业务事件优先，调整项有依据才补

先确认差异对应的具体会计科目及展示符号，再用 `custodian_events.list` 查既有事件，结合成交费用、申赎、产品分红、费用实付、利息与结算材料解释。

|已核实原因|选择与避免|
|---|---|
|漏记申购、赎回、分红或费用业务|优先补对应真实托管事件；申赎还需核对开放日、申赎单位净值和份额策略，不能只填金额|
|已有事件金额、日期或科目错误|按原事件 ID 更正；`custodian_events.update` 是整体覆盖，需要保留的字段须一并提交，不只发一个金额|
|明确的科目调整依据，而非可还原的缺失业务|限定科目、日期和金额，用 `subject_adjusted`；区分调增、调减、调整到，并说明对净资产及后续日期的影响|
|科目展示或估值表分类不一致|先核对映射、币种与负债展示口径；不因名称近似选一个科目调平|
|原因未查明|保留差异并请求缺少的凭证；不能用“其他应收/应付”暂时填平以标记完成|

例如：复查成交与事件后，独立业务凭证确认目标日需将“其他应收款”调增 100 元，且用户已授权，才考虑下列**构造写入示例**：

```python
result = rqamsh.custodian_events.create(
    resource=product_id,
    data={
        "custodian_event_type": "subject_adjusted",
        "date": date,
        "amount": 100.0,
        "adjust_target": "other_receivable",
        "adjust_operation": "increase",
        "remarks": "依据已确认的科目调整凭证",
    },
)
```

这段不是看到差额就自动执行的策略。`increase` 的 100 是本次增量，`adjust_to` 的金额则是目标余额，两者不能互换；负债科目必须按[科目及调整语义](../../custodian_events.md#事件类型与计算影响)判断，不照差异正负机械选方向。

`create` 返回插入条数而非新事件 ID；写入前保存该日期相关记录基线，写后用同范围 `list` 核对新增 ID、业务字段与实际条数。并发或结果不明无法唯一确认时，停止追加和清理，保留待核实结论，不按名称或金额猜测删除。更多规则见[托管事件写入](../../custodian_events.md#create)。

### 4.4 份额与净值仍不同：回查输入链，不直接倒推净资产

先核对申赎事件、份额策略及分类归属，再看份额事件；不能默认独立调整份额。数量、价格、现金、应收应付都核实后，再检查费用计提、产品分红、汇率、累计净值口径和历史日期链。

同日净资产相等也不能证明份额、单位净值、累计净值都正确；当日差异消失也不能证明后续日期没有影响。三级估值表只有汇总科目时，也不能从逐券差异为空推断逐笔成交完整，应按[三级估值表边界](../../reconciliation.md#三级估值表覆盖)核实可比较范围。相关口径只查[头寸字段](../../fields/balances.md)，不在案例另造一套公式。

若只剩累计单位净值差，先核对产品的[累计净值模式](../../fields/products.md#valuationsettings)及[对应舍入规则](../../fields/balances.md#acc-unit-net-value)，判断参照资料是否采用相同精度。金额、份额、单位净值和累计单位净值分别核验，不能把金额容差直接套到净值字段上；已由口径解释的残留也应单列告知用户，不再补流水或调整净资产来消差，未获接受前不据此标记全部完成。

## 5. 写入计划：把诊断与动作分开

通用授权流程按指南的[写操作计划卡](../../guide.md#6-写操作计划卡)。落实到本例，计划应指出：是补 27 日的漏录成交，还是依据独立凭证调增 28 日的其他应收款，抑或明确采用某日估值表；三种动作不能互换，也不共享隐含授权。新增覆盖、删除或扩大日期范围要另行确认。

有封账、权限不足、材料不明或计算失败时，报告具体阻塞，不擅自解封、换产品、改数据源或反复提交。写入超时和部分失败时，先只读核对实际落库结果；不能把“没收到成功”当成“没写入”。

## 6. 回到同一比较点，证明业务修正有效

指南的[任务完成条件](../../guide.md#task-readiness)要求结果可验收；本例用下面这些日期、差异组和记录证明修正有效。

1. 读回实际修改的流水、事件或报告，确认对象、ID、日期与授权字段正确；未修改项保持不变。
2. 按同一整体截止时间检查计算状态，再用 `balances.get` 核对根因实际发生日到用户截止日之间的受影响状态，包含原始差异日和后续日期；必要时检查更早基线未被误改。`normal` 不是内容正确的证明，仍须核对日期与业务字段；若中间有新的覆盖或其他来源切换，分段核实，不假定一次补录会消除全部差异。
3. 重读相同差异组；数量修正后重新检查现金与净值，不沿用修正前差额。仍不一致则回到对应输入层，不反复累加调整。
4. 差异已消除，或剩余项已经用户明确接受且要求标记时，才用 `reconciliation.mark` 记录完成与备注；再用 `list` 读回。`mark` 不修正估值，也不触发重算。
5. 交付对象和日期、已解释/已修复项目、验证范围、剩余差异及缺少证据。不能只回“已对账”。

例如一份合理的回答是：“已追溯到 27 日一笔未录入成交，28 日差异由前序持仓延续，并非当天漏买；按原业务日期补录并重算后，已核验区间的数量与现金恢复一致。另一期货价格差已由产品结算价设置及报告收盘价依据解释，尚待确认是否接受该口径，因此未标记全部完成。”这是回答结构示例，不是实际执行结果；实际交付须列明核验区间及尚缺的证据。

## 7. 如果目标就是采用估值表，走另一条明确分支

用户明确要求“该日以托管估值表为准”，且报告内容、产品模式、日期和影响范围已核实后，才评估 `reconciliation.auto`。它写入覆盖并提交重算，不是“查一遍差异并确认”。成功返回可以是 `None`；仍要等计算并读回目标日及后续结果，同时检查 `auto_reconciled` 与 `done`。

使用覆盖可能使结果与估值表一致，但不证明真实成交、申赎或产品分红已经完整维护。不能为消除差异悄悄采用估值表，也不能把覆盖生成的影子流水当作补齐真实流水。

如需撤销，单独确认 `undo_auto` 的日期及影响。它删除覆盖输入、保留报告并触发重算；结果取决于当前业务输入，不承诺恢复某次历史快照。删除覆盖还可能重置人工完成标记，详见[采用](../../reconciliation.md#auto)与[撤销](../../reconciliation.md#undo_auto)。

## 可选受控演示：观察保存、标记、采用与撤销

[脚本](run.py)只演示上述状态区别：新建混合产品、采用开始日报告建立基线，再上传目标日报告但不采用，人工标记、采用、撤销，最后清理本次报告与产品。它**不实现上文的漏成交诊断、科目调整或任意产品自动修复**，也不应直接用于现有业务产品。

```console
python docs/demo/reconciliation-controls/run.py \
  --base-url https://ams.example.com \
  --workspace-id <授权演示空间ID> \
  --name harness-demo-20261102-reconciliation-<8位随机十六进制> \
  --confirm harness-demo-20261102-reconciliation-<同一随机后缀> \
  --journal ./reconciliation-example.jsonl \
  --report ./reconciliation-example.json \
  --allow-writes
```

名称前缀和八位十六进制后缀是该脚本的参数约束，不代表真实产品或内部运行标识；每次使用新的随机后缀，`--name` 与 `--confirm` 必须完全相同。运行前确认脚本固定的构造日期、金额与全部副作用；可用 `--check` 只做本地参数检查，不连接服务或创建文件。日志与报告必须是新路径。清理仅限本次创建并核实归属的对象；按日期删除报告不是按 ID 原子删除，无法确认当前归属时不得继续。

## 换个条件，自己选择路径

- `done=true` 但用户刚补了一笔历史成交：能沿用原完成结论吗？需要重查哪些输入和日期？
- 报告不存在，但产品开启了自动覆盖：补导前为什么必须说明可能改变估值？
- 已有报告且 `auto_reconciled=true`，用户要查漏成交：为什么不能凭净值相等结束，也不能未经授权撤销？
- 持仓少 20 股，同时现金多一笔成交金额：为什么应先查流水，而不是分别补数量与现金调整？
- 当天成交完整，但前序持仓已少 20 股：应向前追到哪里，什么证据能证明根因，为什么不能在当天补一笔差额成交？
- 送股数量异常：登记日持仓、到账时点、在途及手工/自动权益分别如何核实？当前环境无法使用 RQData 时还能查哪些来源？
- 产品按期货结算价估值，报告按收盘价估值：怎样用设置和同日行情解释差异，为什么解释成立后仍不能擅自改价或标记完成？
- 只剩管理费应付差：应查实际费用支付、计提配置还是直接写调整项？还缺什么证据？
- 科目调整提交超时：下一步应查什么，什么情况下必须停止，为什么不能重发一次？

参数、返回与字段以[对账](../../reconciliation.md)、[流水](../../trades.md)、[估值报告](../../valuation_reports.md)、[托管事件](../../custodian_events.md)及当前 `rqamsh schema` 为准。
