# 收益异常定位（returns-diagnosis）

> 学习案例，不是接口清单，也不是执行报告。本页没有执行任何业务调用；产品、日期、价格、成本与数值都是构造的。百分比是展示约数，不冒充接口逐字回执；字段、枚举、公式与返回位数以 [`docs/`](../../index.md) 和当前 `rqamsh schema` 为准。

## 学习目标

- 把“股票涨了”“持仓亏着”“产品收益不对”拆成四个口径，任何两个都不能互相替代。
- 用公开指标读区间收益，先核对区间前基点、净值与份额、产品分红、数据源与日历，再解释差额。
- 同口径仍不一致时先列候选解释，再用“首次差异日 → 同一条流水主键 → 原始凭证”排除到唯一根因；在已批准范围内更正后，用计算状态与读回结果证明生效、交代未变基线。

## 构造前提与场景

统一前提：人民币；产品只有一个多头股票和一个活期存款科目；无负债、无其他权益事件、无费用、无申赎、无产品分红、无估值表覆盖。数值只在这个前提下互相勾稽，换了前提要重算。净值由整数份额与两位小数价格得出，1.150、1.153、1.162、1.166、1.186、1.196 都是构造值的原值，本页没有截断；接口实际返回的位数与舍入仍以权威页为准。

> 用户说：6 月这只产品应该赚了 4.6%，系统只给 4%。我的股票今天涨了 2%，持仓却还亏着，是不是收益算错了？

|项目|构造值|说明|
|---|---|---|
|产品|示例产品 R（简称 `P`，ID 写作 `<P 的产品 ID>`）|交易流水数据源，账户“示例交易账户”|
|份额|1,000,000.00 份|区间内无申购赎回|
|持仓身份|`000001.XSHE`，`asset_class=stock`，`direction=long`|代码仅作示例；另有一个 `current_deposit` 现金科目|
|2026-05-29 至 05-31、06-15|30,000 股，估值价 11.80；现金类金额 796,000.00；净资产 1,150,000.00；单位净值与累计单位净值 1.150|构造前提是这四天都有可用估值摘要：05-31 是 06-01 区间的“前一天”基点，06-15 是变式的 T-1|
|2026-06-16 买入|10,000 股 @ 11.00，佣金 0|教学简化，不代表实际费率；真实成交日，系统一度记到 06-17；此后现金类金额 686,000.00|
|构造收盘价|06-16 为 11.90，06-17 为 12.00，06-29 为 12.50，06-30 为 12.75|06-30 当日 +2.00%|
|持仓成本（06-30）|524,000.00；含费均价 13.1000|原有 30,000 股成本 414,000.00 ＋ 本笔 110,000.00|

## 第 1 步：先把“涨”和“赚”拆成四个口径

|用户说的|实际口径|读哪个字段|本案例构造值|不能替代|
|---|---|---|---|---|
|“股票涨了 2%”|单只证券的行情涨跌|`positions[].fair_value`（股票取未复权收盘价，或命中的[人工公允价](../../custom_instruments.md)）|12.50 → 12.75，+2.00%|不是产品收益率，也不说明这笔持仓赚没赚钱|
|“持仓还亏着”|相对含费成本的浮动盈亏|`positions[].floating_pnl`（见[逐仓字段](../../fields/balances.md#position-calculation)）|−14,000.00 元；约 −2.67%|不是当日盈亏，也不是产品收益率|
|“今天赚了多少”|产品当日收益|`daily_pnl`（金额）、`daily_returns`（比例）|+10,000.00 元；约 0.8432%|不是区间收益，也不是股票涨幅|
|“6 月赚了多少”|产品区间收益|`returns_summary.total`|约 0.04，即约 4%|不是把个股涨幅按仓位换算，也不是浮亏除以成本|

字段定义、逐仓计算与精度只在[头寸字段字典](../../fields/balances.md#balance-calculation)；指标怎么选序列、对齐和汇总只在[指标公式](../../analytics/metrics.md#indicator-inputs)。本页不复制公式，也不展示推导。

## 第 2 步：股票涨、持仓亏、产品小涨，可以同时成立

|观察项|2026-06-29|2026-06-30|
|---|---|---|
|持仓数量 / 方向|40,000 / long|40,000 / long|
|估值价 `fair_value`|12.50|12.75|
|持仓市值 / 累计成本|500,000.00 / 524,000.00|510,000.00 / 524,000.00|
|含费均价 / 浮动盈亏|13.1000 / −24,000.00|13.1000 / −14,000.00|
|持仓当日盈亏|—|+10,000.00|
|净资产|1,186,000.00|1,196,000.00|
|单位净值 / 累计单位净值|1.186|1.196|
|产品当日收益率|—|约 0.8432%|

三个结论同时成立：行情涨了 2.00%，这是单只证券的价格变化；持仓仍浮亏，因为含费成本 13.10 高于现价 12.75，浮亏是相对成本的历史结果；产品只涨约 0.84%，个股涨幅被仓位稀释。

> **两条边界。** 不要把单只证券当成全产品：这里能得出产品当日收益，是因为前提限定为一只多头股票加存款，真实产品要先按 [positions](../../fields/balances.md#position) 的全部仓、方向和资产品种核对。反过来也常错：浮亏不代表今天亏钱，这笔持仓今天赚了 10,000.00 元，浮亏是尚未实现的累计差额；用浮亏解释当日收益、或用行情解释产品收益，都会得到错误结论。

## 第 3 步：区间收益按公开指标读

```python
result = rqamsh.analytics.indicators(
    resource="<P 的产品 ID>",
    start_date="2026-06-01",
    end_date="2026-06-30",
    extra_indicators=["returns_summary", "asset_series"],
)
```

读回至少看 `returns_summary.total`、`last_unit_net_value`、`asset_series.daily[]` 的 `date`、`daily_returns` 与两种净值。`asset_series` 是按频率分组的对象，`asset_series.daily` 才是逐日记录数组，不是“字段 → 日期”映射；本案例构造结果约为 0.04 和 1.196，具体数字与位数以读回为准。

### 区间核对五项

净值和净资产类时序用公开的指标序列读，逐日形如 `{指标名: {日期: 值}}`；序列不承诺带齐所有字段，份额、累计每份分红等只在必要日期用单日 `balances.get` 或 `unit_events.list` 读，不假设字段一定存在，也不编造值：

```python
series = rqamsh.analytics.series(
    resource="<P 的产品 ID>", start_date="2026-05-28", end_date="2026-06-30",
    indicators=["unit_net_value", "acc_unit_net_value", "total_equity", "daily_pnl", "cash"],
)
```

|核对项|读什么|本案例应看到|不一致时怎么办|
|---|---|---|---|
|区间前基点|指标序列的日期键与 `unit_net_value`（序列从 05-28 起，可直接看起点落在哪一天）；最早可用日用 `balances.field_earliest_date`|构造前提：05-29 至 05-31 都有可用估值摘要，06-01 区间的起点是 05-31，两种净值都为 1.150|起点取“请求区间前一天”，不是“上一个交易日”，不能假定产品都会自动回退到最近估值日；起点缺失或为 0 时该分支按 1 处理，必须先说明，也不能改用 06-01 当天净值或另算“区间末 ÷ 区间首”|
|净值与份额|同序列两种净值；份额用 `unit_events.list` 的 `unit_changes[].units`|份额全区间 1,000,000，两种净值相同|份额有变化时“金额差除以期初净资产”会失真，仍以指标为准；`units` 为 `null` 是估值未产出，不是零份额|
|产品分红|两端各读一次 `balances.get(..., fields=["acc_unit_dividend"])`；必要时查 `custodian_events.list` 的 `product_dividend_paid`|区间内累计每份分红为 0，两种净值不分叉|有分红时两条净值分叉，必须走累计净值口径，不能只看单位净值|
|数据源与覆盖|`products.get` 的 `data_source`；`reconciliation.list` 的 `auto_reconciled`、`done`；`valuation_reports.list` 区间内报告|`trade`，区间内无[估值表覆盖](../../reconciliation.md#valuation-report-overwrite)|有覆盖时净资产按报告重建，行情无法单独解释当天净值，也不能用覆盖后净值反推流水对错|
|日历|产品的 `calendar`、`market_data.trading_dates` 与指标序列的日期键|请求区间与必要基点可读；06-15、06-16、06-17、06-29、06-30 都在序列里|先区分产品日历不包含该日、结果未就绪和实际缺输入；不同指标对缺值有沿用前值、后向补齐或补零等不同分支，按[指标输入整理规则](../../analytics/metrics.md#indicator-inputs)核实，不能把已补齐序列当原始输入完整的证据|

`returns_summary.this_month` 是从区间末回看一个月的滚动窗口，不是本自然月；要自然月就用 `start_date`/`end_date` 加 `total`。

### 用户算的 4.6% 错在哪

|用户的算法|构造结果|问题|交付口径|
|---|---|---|---|
|以初始资金为分母算区间增量|约 4.6%|把成立时的面值当成区间起点，混了“成立以来”和“本区间”|约 4%（`returns_summary.total`）|
|以成本为分母算浮亏|约 −2.67%|持仓口径，且是相对成本的历史差额|约 4%|
|直接用个股涨幅|+2.00%|单一持仓行情，不是产品净值变化|约 4%|
|以期初净资产为分母算区间增量|约 4%|无申赎、无分红时与指标一致，可作守恒核对；有出入金或分红会失真，也不是“已返回的指标值”|约 4%|

最后一行不是另一种算法，而是本前提下的核对：对上说明输入自洽，不能把核对值当成接口返回。

## 第 4 步：同口径仍不符，先列候选再定位

> 用户接着说：06-16 产品明明买了 10,000 股，股票当天也涨了；可系统 06-16 的日收益只有约 0.26%，06-17 反而有约 1.13%。拿 06-16 当期末的区间都比业务记录少约 0.78 个百分点。

|读回项|2026-06-15|2026-06-16（系统）|2026-06-16（按凭证应为）|2026-06-17（系统）|2026-06-17（按凭证应为）|
|---|---|---|---|---|---|
|持仓数量|30,000|30,000|40,000|40,000|40,000|
|现金类金额|796,000.00|796,000.00|686,000.00|686,000.00|686,000.00|
|净资产|1,150,000.00|1,153,000.00|1,162,000.00|1,166,000.00|1,166,000.00|
|单位净值|1.150|1.153|1.162|1.166|1.166|
|产品当日收益率|—|约 0.2609%|约 1.0435%|约 1.1275%|约 0.3442%|
|持仓当日盈亏|—|+3,000.00|+12,000.00|+13,000.00|+4,000.00|

### 候选解释与排除

先只描述观察：06-15 一致；06-16 首次出现数量与现金的差；06-17 起两者又一致，两天的当日盈亏合计都是 16,000.00 元，只是金额分到了不同日期。“一天位置不同”只是候选之一，先列全，再用证据逐条排除：

|候选解释|需要的证据|本案例的排除依据|
|---|---|---|
|录入时日期错记|记录的 `datetime`/`trading_date` 与原始凭证不符，其余字段一致|凭证成交在 06-16，记录标 06-17；数量、价格、账户、标的一致|
|期初或初始化持仓的建仓日不同|产品起始日、初始化流水或初始化报告|初始化记录核对无误，06-15 数量与现金一致，06-16 没有另一笔初始化输入|
|权益事件（分红、送转）在途或登记日不同|证券权益公告或对应外部权益数据、登记日持仓、权益流水与 `positions[].extras` 在途记录；产品分红另查托管事件|构造前提为区间内没有证券权益或产品分红；实际排查必须取得对应证据，不能由产品 `acc_unit_dividend=0` 推断没有证券分红送转|
|其他资金流（划转、费用、申赎）|`net_cash_in`、同期其他流水、`unit_events.list`|区间内无其他流水与份额事件，现金差恰为买入金额|
|某日估值未就绪或被覆盖|`products.compute_state`、`reconciliation.list`、`valuation_reports.list`|区间内无覆盖，06-16 与 06-17 均可读|

只有“凭证与记录逐字段对齐、且其余候选都有排除依据”时才能写“日期错记”。证据不全时只列候选与缺口，不写根因。定位后也不要用下面这些“修法”：

|错误做法|会发生什么|
|---|---|
|改今天的成本或含费均价|06-30 的 524,000.00 与 13.1000 在两种口径下相同，改动会凭空改变浮亏与净值|
|改某一天的估值价，或补一笔现金流出再冲回|污染行情口径或新增无凭证流水，后续日期的现金与净值被重复调整，审计链断裂|
|删除重录这笔买入|记录 ID 变化，原导入链断开；只有原记录不可修复且单独授权时才考虑|

## 第 5 步：追到同一条流水主键与原始凭证

```python
records = rqamsh.trades.list(
    resource="<P 的产品 ID>", start_date="2026-06-15",
    end_date="2026-06-18", order_book_id="000001.XSHE",
)
record = rqamsh.trades.get(resource="<P 的产品 ID>", trade_id="<记录 _id>")
```

列表主键是 `_id`，不是 `foreign_id`。构造读回：`datetime` 为 2026-06-17 10:12:00、`trading_date` 为 2026-06-17、`transaction_type` 为 `buy`、数量 10,000、价格 11.00、佣金 0、账户“示例交易账户”、来源 `manual`、外部流水号 `demo-broker-20260616-0007`，录入时间晚于成交时间。写前用 `get` 保存完整原记录。

原始凭证是券商成交回报，显示成交在 2026-06-16 14:20:00，其余字段与记录一致，成交编号与外部流水号一致。若记录来自文件导入，再用 `confirmations.list` 核对 `total_parsed` 与 `total_registered`，不相等时用 `confirmations.get(..., status='failed')` 看失败项；凭证日期区间按操作时间过滤，不是被导入数据的业务日期。

|观察|结论|
|---|---|
|同一 `_id`、同一外部流水号，只有日期不同，且凭证支持 06-16|日期错记，进入更正计划|
|多条候选、外部流水号不同|停止，要求按成交编号或成交时间确认，不能都改|
|列表没查到或只查了主表，但批次 `total_registered < total_parsed`|该批有登记失败项或历史记录在副表：先补失败项、先确认主/副表，不要断言“缺一笔”|
|来源是 `intraday_upload`/`settlement_upload`|先判断是否应重传对应文件，不要用结构化 update 绕开文件流程|

## 第 6 步：计划卡与授权范围

通用边界见[写入范围与授权](../README.md#6-写操作计划卡)；下面只填本例这一条日期更正的对象、证据与读回范围。

```text
对象：示例产品 R（<P 的产品 ID>），账户“示例交易账户”
范围：仅流水 <记录 _id>（外部流水号 demo-broker-20260616-0007）一条；依据是原始成交凭证，候选解释已排除
写入字段：datetime → 2026-06-16 14:20:00
预期读回：服务端按成交时间与资产品种推导 trading_date，股票本例应为 2026-06-16
动作：trades.update（不改交易类型、来源、数量、价格、费用、账户、标的）
会改变什么：06-16 起的数量、现金、净资产、净值与日收益，并触发相关日期重算
读回：06-16、06-17、06-30 的单日报表；同区间指标；compute_state 与 execution_id
失败时：保留记录 ID 与 execution_id，未知结果先只读核实，不重放
```

授权按**已批准范围**执行：本任务批准的是这一条流水的日期更正、由此触发的必要重算，以及读回核对。删除、重录、改产品配置、采用或撤销估值表覆盖、批量改写其他记录，都需要另行授权，不因为“反正都是修错”就并进来。

写前还要确认旧日 06-17 与新日 06-16 均未封账（`closing_date` 与 `reconciliation.list` 的 `closed`）、本人对该产品可写（`products.list` 的 `permissions` 行，`is_owner=true` 按最高级别处理），并先查一次 `compute_state` 记下 `execution_id` 作为基线，否则写后无法判断结果是不是新算出来的。只读身份若被对账状态接口拒绝，应明确该项未核验，不试探写入；各查询的级别见[最低权限要求](../../permissions.md#逐操作最低权限级别)。

## 第 7 步：执行、状态与读回

```python
before = rqamsh.products.compute_state(resource="<P 的产品 ID>")
result = rqamsh.trades.update(
    resource="<P 的产品 ID>",
    trade_id="<记录 _id>",
    data={"datetime": "2026-06-16 14:20:00"},
)
```

只提交 `datetime`；普通 `trades.update` 不允许直接修改 `trading_date`，它由服务端依据成交时间与资产品种重新推导。写后用同一记录 ID 读回两个字段，确认本例的交易日为 2026-06-16，不能把预期交易日当作请求字段提交，详见[流水更正](../../trades.md#update)。

`effect_count` 为 1 只说明实际改了一条；为 0 表示提交内容与现值一致，不代表记录不存在。`updated._id` 应与原 `_id` 相同，不同则说明发生了新增而非更新，立即停止核对。返回与 `updated` 原样保留。

```python
state = rqamsh.products.compute_state(resource="<P 的产品 ID>")
day_16 = rqamsh.balances.get(
    resource_or_resources="<P 的产品 ID>", date="2026-06-16",
    fields=["total_equity", "units", "unit_net_value", "acc_unit_net_value",
            "acc_unit_dividend", "daily_pnl", "daily_returns", "cash", "positions"],
)
```

`fields` 只投影顶层字段，不能传 `positions.quantity` 这类嵌套路径。现金不要只看顶层 `cash`：它可能缺失或为 `null`，要按 `positions` 中 `asset_class` 属于现金类的记录（本案例为 `current_deposit`）核对金额。

状态处理：`computing` 在本次整体截止时间内只读重查；`error` 立即停止并保留诊断；`normal` 仍要与写前基线比较 `execution_id`，并确认目标内容已更新——`normal` 也可能对应旧结果。**状态未知或字段缺失时停止诊断，不把“读不到”当完成，也不反复提交写入。** 等待超时只表示停止等待，先确认原请求结果。读回结果如下：

|核对项|更正前|更正后|性质|
|---|---|---|---|
|06-16 数量 / 现金类金额|30,000 / 796,000.00|40,000 / 686,000.00|受影响的输入状态|
|06-16 净资产 / 单位净值|1,153,000.00 / 1.153|1,162,000.00 / 1.162|受影响结果|
|06-16 当日收益率 / 当日盈亏|约 0.2609% / +3,000.00|约 1.0435% / +12,000.00|受影响结果|
|以 06-16 为期末的区间累计|偏低|与业务记录一致，差约 0.78 个百分点|受影响区间|
|06-15 及以前的状态|30,000 / 796,000.00 / 1.150|相同|未变基线|
|06-17、06-29、06-30 的对应状态|见前表|各日更正前后相同|未变基线（各日相同，不是此后每天固定为同一值）|
|06-17 当日盈亏|+13,000.00|+4,000.00|受影响结果；两天合计仍为 16,000.00|
|06-30 估值价、成本、含费均价、浮动盈亏|12.75 / 524,000.00 / 13.1000 / −14,000.00|相同|证明没有改成本或行情|
|全月 `returns_summary.total`|约 4%|约 4%|未变基线；不能解释用户的 4.6%|

**区间是否变化要写清条件。** 本例所用的单产品净值差口径，只有先确认区间基点与期末的净值状态都未改变，才能判定累计不变：两端都在错日前、都在收敛后，或基点早于错日且期末不早于收敛日，均属本例的不变范围。若基点恰为 06-16，则累计会变，例如查询 06-17 起的区间时依赖前一天的净值，不能只看期末已收敛。累计不变也不等于风险指标不变：波动、回撤、胜率依赖日收益路径，两天的收益被重新分配后可能变化，必须重读而非预设变化方向。本案例全月基点在 05-31（错日之前）、期末在 06-30（收敛之后），所以全月累计不变；这说明的是“这笔更正解释不了用户的 4.6%”，不是“全月一定不受任何历史错误影响”。

## 交付什么

回答结构见[业务交付](../README.md#7-结果翻译)，不再复制通用交付清单。本例应把两件事分开说明，下面是**构造结论示例，不是执行回执**：

> 6 月区间收益约 4%，用户手算的约 4.6% 使用了成立时的初始资金，而不是本区间基点。06-30 股票上涨 2%，但现价仍低于含费成本，因此持仓浮亏 14,000 元；产品当日收益约 0.8432%。这三件事不矛盾。
>
> 另一个已核对的问题是：一笔 06-16 成交被记到 06-17。按凭证更正原记录的成交时间后，06-16 数量由 30,000 股恢复到 40,000 股，当日盈亏由 3,000 元恢复到 12,000 元；06-17 当日盈亏相应变化，两日合计仍为 16,000 元。全月两端净值未变，所以这笔更正不改变全月约 4% 的累计收益；以 06-16 为基点的区间及日收益路径指标另行复查。

实际交付须用本次读回补上目标产品与流水 ID、写前/写后执行序号、已核验日期和未解决项；若没有执行更正，第二段只能写诊断与拟修方案，不能写成“已经恢复”。

## 停止与失败边界

### 资料不足

|情况|动作|
|---|---|
|只有行情或口述，没有成交凭证、托管对账单或估值表；或 `trades.list` 分页不全、只查主表，凭证 `total_registered < total_parsed`|说明缺什么、影响哪一步、需要补哪份材料；先补全或先修失败项，不判断“缺一笔”|
|读不到 `positions`、净值或份额（权限、`null`、缺日）|报缺口并列已就绪部分，不用相邻日期、上一交易日概览或 0 替代|
|产品、账户、日期或记录不唯一|停止，列候选让业务确认|

### 疑似计算缺陷

|观察|处理|
|---|---|
|同一产品、同一区间、同一分支连续读回不一致，且已排除并发写入与重算|保留两次返回原文、请求参数、日期、`update_time` 与 `execution_id`|
|输入齐全（流水、行情、权益、份额、无覆盖）仍有数量级无法解释的差异|记录差异位置与量级，核对分支是否适用于该产品|
|`compute_state` 持续 `error`，且不是缺输入或权限问题|保留错误原文、`execution_id`、目标日期，报告待服务端排查|

判断前要先限定分支与精度：只在“单产品、有份额、有累计与单位净值、无估值表覆盖、平台精度与舍入方式已知”的同一分支内比较；比较用事先约定的容差，不做浮点严格相等。`acc_unit_net_value` 随收益变动是正常现象，分红为 0 时它照样会动，不能当作缺陷判据。证据不足不是缺陷——先补输入、权限与未就绪判断。

### 未授权不能写

- 批准范围之外的动作不执行：删除、重录、改产品配置、批量改写其他记录、采用或撤销估值表覆盖；也不用探测性写入验证权限，或靠改配置绕过封账与来源限制。
- 读得不到位时交付“已确认 ＋ 未确认”清单，不为了让结果合理去改流水、改估值价或换口径重算。

## 变式问题

1. 如果改为支持夜盘的期货，成交时间是 06-17 夜间、交易日应记 06-18：更正 `datetime` 后应核对哪个派生交易日？为什么不能直接提交 `trading_date`，也不能只看自然日？
